## 1. 제품 배경

사용자는 운동과 식단을 기록하더라도 "그래서 오늘 무엇을 먹어야 하는지"를 스스로 결정해야 한다. 특히 체중 감량, 근육 증가, 체형 개선처럼 신체 변화 목표가 있을수록 식단 선택의 부담은 커진다.

기존 식단 기록 기능은 섭취한 음식을 남기는 데 초점이 있다. 이번 기능은 기록 이전 단계에서 사용자가 먹을 수 있고, 먹고 싶고, 목표에 맞는 식단을 제안해 기록 행동까지 이어지게 만드는 것을 목표로 한다.

핵심 가치는 다음과 같다.

- 사용자는 매번 식단을 계산하지 않아도 된다.
- 알러지나 기피 식품이 있는 사용자는 추천을 더 신뢰할 수 있다.
- 목표 영양치와 실제 식단 기록 사이의 간극을 줄인다.
- 추천 식단을 원터치로 기록해 기록 피로를 낮춘다.

## 2. 사용자 문제

### 주요 문제

1. 목표는 설정했지만 하루 식단으로 어떻게 바꿔야 할지 모른다.
2. 식단 추천 서비스는 많지만 알러지와 기피 식품을 충분히 반영하지 않는 경우가 많다.
3. 한국 음식과 한식 메뉴 기준의 추천 품질이 낮으면 실제 생활에 적용하기 어렵다.
4. 추천을 받아도 다시 식단 기록에 입력해야 하면 번거로워서 이탈한다.

### 사용자 질문

- 내 목표에 맞게 오늘 무엇을 먹으면 좋을까?
- 내가 못 먹거나 안 먹는 음식이 빠져 있을까?
- 이 식단이 내 칼로리와 단백질 목표에 얼마나 맞을까?
- 마음에 드는 끼니만 바로 기록할 수 있을까?

## 3. 기능 목표

사용자가 알러지와 기피 식품을 등록하면, 앱은 해당 조건을 반영해 목표 영양치에 맞는 하루 식단을 추천한다. 추천 결과는 끼니 단위로 확인하고, 마음에 드는 끼니를 기존 식단 기록으로 저장할 수 있어야 한다.

v1의 목표는 "완벽한 개인 맞춤 코치"가 아니라 "안전한 제외 조건과 목표 영양치에 맞춘 실용적 하루 식단 제안"이다.

### 성공 조건

- 사용자가 알러지/기피 식품을 설정할 수 있다.
- 추천 식단은 등록된 제외 조건을 위반하지 않는다.
- 추천 결과는 목표 유형별 열량·단백질·탄수화물 hard constraint를 위반하지 않는다.
- 사용자는 추천 끼니를 원터치로 식단 기록에 저장할 수 있다.
- 추천할 수 없는 경우에도 이유를 이해할 수 있다.

## 4. 대상 사용자

### 1차 사용자

- 주 2~5회 운동하며 체중 감량, 근육 증가, 체형 개선 목표가 있는 사용자
- 식단 관리를 하고 싶지만 매번 메뉴를 직접 계산하기 어려운 사용자
- 알러지, 편식, 종교적 이유, 건강상 이유 등으로 제외해야 할 음식이 있는 사용자

### 2차 사용자

- 식단 기록은 꾸준히 하지만 다음 식사의 선택지가 필요한 사용자
- 한식 중심의 실생활 메뉴 추천을 원하는 사용자
- 자주 먹는 음식 기반으로 반복 가능한 식단 루틴을 만들고 싶은 사용자

## 6. 제품 원칙

### 6.1 제외 조건은 추천 품질보다 우선한다

알러지와 사용자가 명시한 기피 식품은 목표 영양치보다 우선한다. 추천 후보가 부족하면 억지로 추천하지 않고, 어떤 조건 때문에 추천이 어려운지 안내한다.

"안전 우선"은 의료급 안전 보장이 아니라 **검증된 데이터 계약 안에서 제한 조건을 절대 완화하지 않고, 불확실성과 회피 근거를 투명하게 보여주는 것**으로 해석한다. 원재료·알러젠 프로필을 검토하지 않은 식품은 알러지 사용자의 추천에서 제외한다. 후보가 부족하면 미검토 식품을 통과시키지 않고 실패 사유를 설명하며 검증 풀 보강 대상으로 집계한다.

### 6.2 사용자는 "왜 이 식단인지" 이해할 수 있어야 한다

추천 결과에는 최소한 다음 정보가 보여야 한다.

- 목표 대비 칼로리
- 목표 대비 단백질
- 포함된 끼니 구성
- 적용된 제외 조건
- 추천을 구성한 기준
- 알러젠·영양 데이터의 검증 근거와 마지막 검증일
- 추정 섭취 기록 때문에 불확실성 여유를 적용했는지 여부

### 6.3 의료 표현을 피한다

이 기능은 사용자의 기록과 선택을 돕는 식단 제안 기능이다. 알러지 진단, 치료, 완전한 안전 보장, 질환별 처방처럼 보이는 표현은 사용하지 않는다.

권장 문구:

> 등록한 제외 조건을 기준으로 추천 식단에서 제외합니다.

피해야 할 문구:

> 알러지 위험이 없는 안전한 식단입니다.

### 6.4 한국 사용자 기준을 우선한다

알러지 태그는 한국 식품 표시기준의 의무표시 알레르기 유발물질을 기준으로 한다. 글로벌 8대 알러젠만으로는 한국 사용자의 실제 등록 요구를 충분히 담기 어렵다.

### 6.5 추천은 기록으로 이어져야 한다

추천 기능의 최종 행동은 "보기"가 아니라 "기록하기"다. 사용자는 전체 식단 또는 끼니 단위로 기존 식단 기록에 저장할 수 있어야 한다.

### 6.6 알러지 회피는 버전된 근거 + 완결 프로필로 운영한다

알러지는 `ALLERGY + ALLERGEN_TAG`로만 등록한다. 알러지 제한이 하나라도 있으면 사용자 선택과 관계없이 verified-only 게이트를 적용하며, 기존 `strictAllergyMode`는 API 호환 기간을 거쳐 폐기한다. 알러지가 없는 사용자는 프로필 미검토만으로 추천 후보에서 제외하지 않는다.

알러젠 근거는 출처별로 보존하며 실제 원재료 포함과 교차접촉 가능성을 구분한다.

| 관계 | 의미 | 알러지 추천 판정 |
|---|---|---|
| `CONTAINS` | 원재료·하위 원재료로 포함 | 제한 태그와 일치하면 제외 |
| `MAY_CONTAIN` | 같은 시설·설비 등 교차접촉 가능성 | 제한 태그와 일치하면 제외 |

각 근거에는 신뢰 수준, 출처, 원문 참조, 근거 버전, 검토일과 유효 상태를 둔다. 더 최신의 동일 제품 공식 전체 라벨은 이전 근거를 판정에서 대체할 수 있지만 이력은 삭제하지 않는다. 서로 다른 유효 근거가 충돌하면 자동 우선순위를 적용하지 않고 추천에서 제외해 재검증 대상으로 보낸다.

| 레벨 | 근거 | v1 의미 |
|---|---|---|
| `DIRECT_VERIFIED` | 단일재료 식품을 식약처 식품분류 코드로 결정적 매핑 | 포함 근거 및 완결 프로필 가능 |
| `LABEL_DERIVED` | 제품 표시 라벨·공식 메뉴의 전체 알러젠 정보 | 포함·교차접촉 근거 및 완결 프로필 가능 |
| `RECIPE_DERIVED` | 표준 레시피에서 재료별 알러젠 합집합 도출 | 포함 발견·차단에만 사용, 통과 근거 금지 |
| `UNKNOWN` | 재료·라벨 정보 없음 | 통과 근거로 사용하지 않음 |

완결 알러젠 프로필은 어떤 표준 버전의 어떤 태그 집합을 검토했는지, 출처·검토일·유효기간·무효화 상태가 무엇인지 표현한다. 포함·교차접촉 근거가 0개여도 전체 범위를 검토한 유효 프로필은 만들 수 있다. 사용자의 모든 제한 태그가 프로필 검토 범위에 포함되고 프로필이 `DIRECT_VERIFIED` 또는 `LABEL_DERIVED`일 때만 통과 가능하다.

제품 사실이나 데이터 버전이 바뀌고 새 완결 자료가 없으면 기존 프로필을 무효화한다. 브랜드·라벨 프로필은 출처별 만료 정책을 적용한다.

사용자 안내:

> 검증된 식품 정보와 등록한 알러지를 기준으로 추천했습니다. 실제 제품과 제조 환경은 달라질 수 있으니 섭취 전 라벨을 확인해 주세요.

## 7. 사용자 경험 흐름

### 흐름 1: 식단 제한 설정

1. 사용자는 마이페이지 또는 식단 기록 화면에서 분리된 `알러지 설정` 또는 `기피 식품 설정`으로 이동한다.
2. 알러지 설정에서는 현재 정책에서 활성화된 표준 알러젠 태그만 선택한다. 알러지/기피 type picker는 두지 않는다.
3. 기피 식품 설정은 기존 식품·카테고리·키워드 기능을 유지하되 알러젠 태그 선택은 제공하지 않는다.
4. 앱은 등록된 제한 조건을 목록으로 보여준다.
5. 사용자는 언제든 제한 조건을 삭제할 수 있다.

필수 화면 요소:

- 분리된 알러지 태그 선택 영역
- 별도 기피 식품 설정 영역
- 등록된 조건 목록
- 제한 조건 안내 문구

### 흐름 2: 오늘의 추천 식단 생성

1. 사용자는 식단 탭 **상단 상시 카드**의 `오늘의 추천 식단`으로 진입한다.
2. 사용자는 끼니 수(간식 on/off 등)를 선택할 수 있다.
3. 앱은 현재 목표와 등록된 제한 조건을 기준으로 추천을 생성한다.
4. 앱은 끼니별 추천 음식, 제공량, 영양 요약을 보여준다.
5. 사용자는 추천이 마음에 들지 않으면 다시 추천을 요청할 수 있다.
6. 사용자는 전체 식단 또는 특정 끼니를 기록한다.

필수 화면 요소:

- 끼니 수 선택
- 하루 목표 대비 요약
- 끼니별 추천 카드
- 적용된 제외 조건
- 다시 추천
- 기록하기
- 추천 실패 상태

### 흐름 3: 추천 실패

1. 사용자가 제한 조건을 많이 등록했거나 영양 목표 계산에 필요한 정보가 부족하다.
2. 앱은 빈 화면 대신 추천 실패 이유를 보여준다.
3. 사용자는 프로필/목표를 보완하거나 제한 조건을 수정할 수 있다.

예시 문구:

> 등록한 제외 조건을 모두 반영하면 오늘의 목표에 맞는 식단을 만들기 어렵습니다. 제외 조건을 조정하거나 직접 식단을 기록해 주세요.

- 저녁
- 간식

v1에서 **사용자가 끼니 수를 선택**할 수 있다(예: 간식 on/off, 3슬롯 이상). 기본 메인 끼니의 표시 순서는 아침→점심→저녁으로 고정한다. 간식을 선택하면 사용자가 `아침~점심`, `점심~저녁`, `저녁 이후` 중 하나 이상을 독립적으로 고르며, 선택한 각 구간에 간식 슬롯을 하나씩 삽입한다. 선택된 순서를 추천 요청과 결과에 동일하게 적용한다. 선택된 끼니에 맞춰 하루 목표 칼로리를 비례 재분배한다. 간식 외 끼니별 세밀한 시간대 지정·간헐적 단식 연동은 향후 확장으로 둔다.

### 목표 반영 방식

추천은 기존 목표와 사용자 영양 목표를 사용한다.

- 활성 목표가 있으면 활성 목표를 우선한다.
- 활성 목표가 없으면 사용자 프로필에 저장된 영양 목표를 사용한다.
- 필요한 프로필 정보가 부족하면 추천을 생성하지 않는다.

목표 유형은 하나의 대칭 허용 오차를 공유하지 않는다.

| 목표 | 핵심 hard constraint |
|---|---|
| 체중 감량 | 추천 열량은 계산된 목표 미만, 단백질은 목표 이상 |
| 체형 개선 | 추천 열량은 계산된 목표 미만, 단백질은 목표 이상 |
| 근육량 증가 | 단백질과 열량은 목표 이상, 과도한 열량 초과 금지 |
| 지구력 향상 | 열량과 탄수화물 하한 충족 |
| 건강 유지 | 열량과 매크로 허용 범위 충족 |

정확한 비율은 버전이 있는 영양 정책과 benchmark로 관리한다. 체중 감량·체형 개선의 열량 상한에는 영양값과 제공량의 불확실성 버퍼를 둔다.

사용자가 설정한 목표일은 희망 일정이다. 목표 변화량과 남은 기간이 권장 범위를 벗어나면 열량을 과도하게 낮추지 않고 달성 가능한 예상 날짜를 제안한다. 목표 열량과 예상 달성일은 일일 측정값이 아니라 주간 추세로 주 1회 조정한다.

당일 운동 소모 열량은 활동 수준 기반 TDEE와 중복될 수 있으므로 식사 예산에 1:1로 더하지 않는다. 목표별 회복 영양 분배를 위한 제한적 신호로만 사용한다.

### 남은 영양량 반영

추천 전에 사용자가 기록한 식단을 일일 목표에서 차감한다. 남은 끼니를 각각 독립적으로 고르지 않고, 남은 하루 전체가 목표별 hard constraint를 만족하도록 공동 최적화한다.

- 새 식단 기록 후 남은 끼니를 다시 계산한다.
- 하루 총량은 hard constraint, 끼니별 열량·단백질 분배는 soft constraint다.
- 사용자 직접 등록·AI 추정 식단도 이미 섭취한 기록으로 반영한다.
- 미검증 섭취 기록은 열량에는 보수적인 상한, 단백질에는 보수적인 하한을 사용한다.
- 이미 상한을 초과했거나 남은 목표가 불가능하면 조건을 완화한 식단 대신 구조화된 실패를 표시한다.

### 제외 조건 우선순위

1. 알러지
2. 직접 제외한 식품
3. 기피 키워드
4. 기피 카테고리

동일한 음식이 목표 영양치에 잘 맞더라도 제외 조건에 걸리면 추천하지 않는다.

## 9. 데이터 활용 방향

### 기본 영양 데이터

현재 프로젝트의 식품 카탈로그를 기본 후보 풀로 사용한다. 다만 v1 추천 후보는 명시적으로 큐레이션한 seed와 `BRAND_OFFICIAL` CSV 검수 항목 중심으로 제한한다. 기존 seed 전체를 자동 추천 후보로 보지 않는다. 공공데이터로 배치 적재된 항목은 검색/기록 품질을 높이는 기반으로 먼저 사용하고, 기본 추천 상태는 `SEARCH_ONLY`로 둔다. 이미 존재하는 식단 기록, 커스텀 식품, 사용 빈도 정보는 추천 품질 개선에 활용할 수 있다.

보수적인 seed allowlist 때문에 추천 식단이 매번 동일해지는 문제를 막기 위해 v1 후보 풀은 최소 규모를 가져야 한다. 전체 추천 가능 seed는 40~60개 이상을 목표로 하며, 단백질·곡류/주식·채소·과일·유제품/간식 대체 후보가 각각 충분해야 한다. 후보 풀이 이 기준에 못 미치면 추천 범위를 무리하게 넓히지 않고 seed/브랜드 후보를 먼저 보강한다.

후속 추천 최적화에서는 총 추천 후보 수를 KPI로 삼지 않는다. 사용자 수요, 부족한 영양 역할, 알러지 조합 커버리지, 검증 비용을 함께 고려해 **추천 실패를 가장 많이 줄이는 식품부터 검증**한다.

식품 카탈로그는 추천 전용 데이터가 아니라 **식단 기록 검색, 식단 기록 영양 계산, 식단 추천 후보 풀**의 공통 기반이다. 사용자가 식단을 직접 기록할 때도 강화된 `food_catalog`를 검색할 수 있어야 한다.

공공데이터와 브랜드 공식 메뉴는 사용자 검색/추천 시점에 외부 API를 직접 호출하지 않고, 사전 배치 또는 관리자 적재를 통해 내부 `food_catalog`에 저장한다.

- 현재 사용 중인 전국통합식품영양성분정보 가공식품/음식 표준데이터 2종은 내부 카탈로그의 기본 공공데이터 소스로 유지하되, v1에서는 대량 자동 추천 승격하지 않는다.
- 식약처 식품영양성분DB정보(`FoodNtrCpntDbInfo02`)는 기존 표준데이터 2종과 중복/필드 커버리지를 비교한 뒤 보강 소스로 병합한다.
- 원재료성식품 표준데이터는 v1 필수 범위에서 제외하고, 식재료 단위 추천이나 장보기 기능에서 후속 검토한다.
- 상위 브랜드 공식 메뉴는 자동 크롤링이 아니라 관리자 CSV/수동 검수 방식으로 일부 적재한다.
- 사용자 커스텀 식품은 검색/기록 가능하지만, 검증 전에는 추천 후보에서 제외하거나 보수적으로 취급한다.
- 공공데이터 항목을 추천 후보로 승격해야 할 필요가 생기면 개별 수정 API보다 `source + food_code` 기준 큐레이션 오버레이 CSV를 별도 운영 작업으로 검토한다.

브랜드 메뉴는 브랜드 단위가 아니라 **메뉴 단위 추천 적합성 게이트**로 판단한다. 예를 들어 와퍼세트나 치킨 한 마리 메뉴는 검색/기록에는 유용하지만 추천 후보에서는 제외 또는 주의 상태가 될 수 있고, 서브웨이·샐러디·프레퍼스처럼 상대적으로 건강한 메뉴는 영양 기준을 통과하면 추천 후보가 될 수 있다.

| 추천 상태 | 의미 |
|---|---|
| `SEARCH_ONLY` | 검색/기록 가능, 추천 제외 |
| `RECOMMENDABLE` | 일반 추천 후보 |
| `RECOMMENDABLE_WITH_CAUTION` | 나트륨·당류·포화지방 등 주의 표시와 함께 추천 가능 |
| `DISABLED` | 데이터 불완전, 검수 실패, 만료 등으로 비활성 |

추천 상태와 별개로 다음 자격을 평가한다.

- 완결 알러젠 프로필 검증
- 목표별 필수 영양 데이터 완전성
- 현실적인 제공량 옵션
- source와 데이터 버전의 유효성
- canonical 식품 그룹의 대표 후보 여부

여러 API의 동일·유사 식품은 source row를 삭제하지 않고 canonical 그룹으로 묶는다. 동일 공식 코드와 고신뢰 식품 fingerprint는 자동 그룹 후보가 될 수 있으며, 이름만 비슷한 경우는 검수 큐로 보낸다. 불확실한 그룹에는 알러젠 검증 결과를 전파하지 않는다.

추천 엔진은 임의 g 대신 공식 제공량 multiplier, 개수 단위, 검증된 중량 step 같은 이산 제공량만 사용한다. 식단 기록하기 화면은 제공량 프리셋을 기본으로 제공하되 실제 섭취량을 위한 직접 g 입력을 유지한다.

### 알러지 데이터

알러지 데이터는 내부 표준 태그를 기준으로 관리한다. 출처별 알러젠 근거와 완결 알러젠 프로필을 분리하고, 외부 AI나 제3자 분석에 최종 회피 판정을 위임하지 않는다.

- 알러젠 근거는 식품·태그·관계(`CONTAINS`/`MAY_CONTAIN`)·출처·버전별로 보존한다.
- 완결 프로필은 검토한 태그 집합과 표준 버전을 명시한다.
- 여러 출처의 원본 근거는 덮어쓰지 않으며, 대체·무효화 이력을 유지한다.
- 포함·교차접촉 근거가 0개인 완결 검토도 표현한다.
- 알러젠 근거와 프로필은 하나의 적재 트랜잭션에서 함께 생성·교체·무효화한다.

신뢰 레벨별 데이터원(본 앱은 상업 서비스 → 공공누리 제0·1유형 또는 "제한 없음"만 사용):

| 신뢰 레벨 | 데이터원 | 라이선스 |
|---|---|---|
| `DIRECT_VERIFIED` | 식약처 식품영양성분DB의 **식품분류 코드**(중/소분류)를 단일재료 알러젠에 결정적 매핑 | 제한 없음 ✅ |
| `RECIPE_DERIVED` | **국민건강영양조사 음식별 식품재료량 DB**(질병청)로 음식→재료 분해 → 재료별 분류매핑 합집합 | **직접 사용 보류**. 사용 시에도 포함 발견·차단 근거로만 활용 |
| `LABEL_DERIVED` | 식약처 **푸드QR**(원재료·알레르기 표시) + **Open Food Facts**(allergens_tags) | 푸드QR 직접 사용 보류 / OFF는 ODbL 출처표시·동일조건·개방 조건 검토 후 제한 사용 |
| 기준표 | 식약처 식품 표시기준 의무표시 대상 | 공개 |

**폐기된 후보:**
- **메뉴젠 API**: 공공누리 **제4유형(상업 이용금지)** 확정 → 상업 서비스 사용 불가.
- **AllergieShield 등 외부 알러젠 API**: 한국 데이터·분류 체계 미스매치 + 사실상 OFF 래퍼 + AI 기반 분석(회피 판정을 외부 AI에 위임 → 본 정책 위반). OFF를 직접 사용한다.

### AI 활용 방향

v1에서는 AI를 핵심 추천 엔진으로 사용하지 않는다.

향후 AI는 다음 용도로 확장할 수 있다.

- 추천 식단의 설명 문구 생성
- 사용자가 싫어하는 스타일을 반영한 대체 식단 제안
- 주간 식단 다양성 개선
- 카탈로그 매칭이 어려운 음식명 정규화 보조

단, 알러지 회피 여부 판단은 AI가 아니라 서버의 제한 조건 검증이 최종 책임을 가진다.

## 10. 운영 원칙

### 알러지 안전 운영

- 알러지 등록 사용자는 고신뢰(`DIRECT_VERIFIED`/`LABEL_DERIVED`) 완결 프로필 검토 식품만 통과시킨다(§6.6). 사용자 Strict 토글로 이 조건을 완화하거나 강화하지 않는다.
- 제한 태그와 일치하는 `CONTAINS` 또는 `MAY_CONTAIN` 근거는 모두 차단한다.
- `RECIPE_DERIVED`는 포함 발견에만 쓰며, 레시피에 태그가 없다는 사실은 통과 근거로 사용하지 않는다.
- 출처별 원본 근거는 보존하고 유효 근거 충돌 시 fail-closed로 차단한다.
- 프로필 만료·무효화·근거 충돌은 유형별 알러젠 재검증 하위 큐에 노출한다.
- 지원 태그는 고정 benchmark와 데이터 커버리지를 통과한 항목만 활성화한다.
- 사용자 커스텀 식품은 `UNKNOWN`으로 취급한다.
- 알러지 관련 사용자 안내는 보수적으로 작성하며, 추천 식품에는 근거 출처와 검토일을 보여준다.

### 추천 품질 운영

- 추천 실패율을 지표로 추적한다.
- 자주 실패하는 알러지 조합과 목표 조합을 확인한다.
- 사용자가 추천 후 실제로 기록했는지 추적한다.
- 추천 식단을 수정하거나 거절한 이유를 향후 수집할 수 있다.
- 추천 후보는 전체 카탈로그가 아니라 `RECOMMENDABLE`, `RECOMMENDABLE_WITH_CAUTION` 상태의 식품만 사용한다.
- 추천 런타임은 DB WHERE 절에서 추천 상태, 카테고리, 제한 조건, 기본 영양 조건을 먼저 적용해 후보 수를 줄인 뒤 엔진에 전달한다.
- 같은 조건에서 항상 같은 식단이 반복되지 않도록 날짜 기반 deterministic rotation을 적용한다. 같은 사용자/날짜/입력은 재현 가능해야 하지만, 날짜가 바뀌면 후보 우선순위가 달라져야 한다.
- 추천 스냅샷과 노출, 재추천, 기록 전환, 항목 삭제·교체 이벤트를 저장한다.
- 재추천 시 선택형 사유를 수집하되 입력을 강제하지 않는다. 단순 미기록은 부정 선호로 해석하지 않는다.
- 사용자 연결 개인화 이벤트는 기본 90일 보관하고 장기 분석은 비식별 집계만 유지한다.
- 추천 스냅샷에는 알러지 정책 버전, 제한 태그, 식품별 프로필·근거 버전을 저장한다. 자유 기피 키워드 원문은 장기 스냅샷·분석 이벤트·운영 로그에 저장하지 않는다.

### 데이터 운영

- 식품 카탈로그는 영양 정보와 알러지 태그의 출처를 분리해 관리한다.
- 사용자 커스텀 식품은 알러지 태그가 검증되지 않은 상태로 취급한다.
- 외부 API 장애가 사용자 검색/추천에 직접 영향을 주지 않도록 외부 호출은 배치/관리자 적재 경로로 분리한다.
- 브랜드 공식 메뉴는 v1에서 자동 크롤링하지 않고 CSV 수동 검수로 관리한다.
- 원재료·알러젠·제품 버전·제공량·영양값이 바뀌면 추천 자격과 관련 알러젠 프로필을 자동 회수하고 재검증한다.
- 관리자 작업함은 하나로 유지하되 영양·제공량, 데이터 만료, 알러젠 만료·무효화·충돌을 유형별 하위 큐로 조회한다.

## 11. 수용 기준

### 제한 조건

- 사용자는 알러지와 기피 식품을 등록할 수 있다.
- 알러지는 활성화된 `ALLERGEN_TAG`로만 등록할 수 있다.
- `ALLERGY + FOOD/CATEGORY/KEYWORD`와 신규 `AVOID + ALLERGEN_TAG`는 UI·API·DB에서 생성되지 않는다.
- 알러지 설정과 기피 식품 설정은 별도 화면으로 제공한다.
- 사용자는 자유 입력으로 제외 키워드를 등록할 수 있다.
- 사용자는 등록된 제한 조건을 삭제할 수 있다.
- 등록된 조건은 다음 추천부터 반영된다.

### 추천

- 추천 결과에는 등록된 제외 조건에 해당하는 식품이 포함되지 않는다.
- 알러지 제한이 있으면 Strict 요청값과 무관하게 verified-only를 적용한다.
- 제한 태그와 일치하는 `CONTAINS` 또는 `MAY_CONTAIN` 근거가 있는 식품은 포함되지 않는다.
- 알러지 제한이 있으면 모든 제한 태그를 검토한 유효 완결 프로필이 없는 식품은 포함되지 않는다.
- `RECIPE_DERIVED` 근거는 포함 발견 시 차단하지만 통과 근거로 사용되지 않는다.
- 비활성 알러젠 정책, 프로필 만료·무효화, 근거 충돌을 조용히 무시하지 않고 구조화된 실패를 반환한다.
- 추천 결과는 `SEARCH_ONLY` 또는 `DISABLED` 상태의 식품을 포함하지 않는다.
- `RECOMMENDABLE_WITH_CAUTION` 식품이 포함될 경우 주의 근거를 표시할 수 있어야 한다.
- 추천 결과에는 끼니별 음식, 제공량, 칼로리, 단백질, 탄수화물, 지방이 표시된다.
- 하루 총합은 목표 칼로리와 단백질 대비 어느 정도 차이가 있는지 표시된다.
- 동일한 후보 풀에서도 날짜가 바뀌면 추천 구성이 일정 수준 달라져야 한다.
- 추천 생성이 불가능하면 사용자에게 이유를 설명한다.
- 이미 기록한 식단을 차감한 남은 목표를 기준으로 추천한다.
- 추천 제공량은 검증된 제공량 옵션 중 하나다.
- 목표별 hard constraint를 만족하지 못한 근접안은 성공 추천으로 반환하지 않는다.

### 기록 연결

- 사용자는 추천된 끼니를 기존 식단 기록으로 저장할 수 있다.
- 추천 끼니 기록은 전용 전환 API에서 현재 제한과 알러젠 근거를 다시 검증한다.
- 추천 전환은 `snapshotId + mealType` 단위로 멱등 처리한다.
- 일반 식단 기록 API는 알러지 추천 계약과 별개로 유지한다.
- 저장된 기록은 일반 식단 기록과 동일하게 조회, 수정, 삭제할 수 있다.
- 추천에서 기록된 식품도 기존 영양 합계와 주간 회고에 반영된다.
- 추천 후보가 아닌 식품도 검색/기록 가능 상태라면 사용자가 직접 검색해 식단에 기록할 수 있다.

## 14. 오픈 이슈

- **음식별 식품재료량 DB 재사용 라이선스** — `RECIPE_DERIVED` 검수 후보 생성이 여기에 의존한다. 라이선스가 확인되지 않으면 해당 source를 사용하지 않으며, 최종 안전 게이트는 `DIRECT_VERIFIED`/`LABEL_DERIVED`만 사용하므로 출시 조건과 분리한다.
- **푸드QR 라이선스** — `LABEL_DERIVED`(가공식품)용. 상업 이용 가능 여부 확인 필요.
- 한국 의무표시 알러지 태그의 앱 내 영문 코드명을 확정해야 한다.
- `DIETARY_REQUIREMENT` — 글루텐 프리 등 검증 속성 기반 식이 기준의 스키마·근거·UI는 별도 후속 기획으로 분리한다.

### 확정된 결정 (2026-06-04)

- **진입점**: 식단 탭 상단 상시 카드.
- **과금**: v1 전체 무료. 프리미엄 게이팅·추천 횟수 제한은 v2 AI 도입 시 재검토.
- **끼니 구성**: 사용자가 끼니 수를 선택(간식 on/off 등). 기본 4슬롯.
- **다시 추천**: v1은 횟수 제한 없는 전체 재추천. 끼니 단위 Swap은 §13 2단계 후보.
- **알러지 회피 모델(역사적 결정)**: 기본 + Strict 2모드는 2026-06-22 결정과 ADR-0005로 대체됐다.
- **알러젠 데이터원**: 식약처 분류매핑(DIRECT) + 음식별 식품재료량 DB 분해(RECIPE) + 푸드QR·OFF(LABEL). **메뉴젠(제4유형)·AllergieShield 폐기.**
- **커스텀 식품**: `UNKNOWN`으로 취급(검증 표시 별도 결정 불요 — 신뢰 레벨로 일원화).
- **식품 카탈로그 운영**: 공공데이터와 검수된 브랜드 공식 메뉴를 사전 적재한 내부 `food_catalog`를 검색/기록/추천의 공통 기반으로 사용한다.
- **추천 후보 정책**: 추천 가능 여부는 브랜드 단위가 아니라 메뉴 단위의 `SEARCH_ONLY`/`RECOMMENDABLE`/`RECOMMENDABLE_WITH_CAUTION`/`DISABLED` 상태로 판단한다.
- **브랜드 메뉴 v1 운영**: 자동 크롤링은 제외하고, 상위 브랜드 일부를 관리자 CSV/수동 검수로 적재한다.

### 확정된 강화 결정 (2026-06-18)

- **핵심 차별점**: 완결 메뉴 생성보다 알러지·기피 hard constraint 안에서 목표별 남은 영양량을 정밀 최적화한다.
- **알러지 기본 게이트**: 알러지 사용자는 완결 프로필 verified-only. 기존 완화 기본 모드는 폐기 방향이다.
- **목표별 정책**: 체중 감량·체형 개선은 열량 상한 미만, 근육량 증가는 단백질 하한 이상을 핵심 절대 제약으로 둔다.
- **목표 기간**: 희망 일정과 예상 달성일을 분리하고 주간 추세로 조정한다.
- **추천 범위**: 이미 기록한 식단을 차감한 남은 하루 전체를 공동 최적화한다.
- **제공량**: 추천은 검증된 이산 제공량, 기록은 프리셋 + 직접 g 입력.
- **후보 풀**: 전체 데이터 건수보다 조건별 추천 성공률을 우선하며 canonical 그룹과 목표별 데이터 완전성을 사용한다.
- **엔진**: greedy에서 제한 시간이 있는 제약 최적화로 단계 전환한다.
- **학습 루프**: 추천 이벤트, 기록 전환, 선택형 재추천 사유를 저장해 개인화와 검증 우선순위를 개선한다.
- **검증**: 고정 benchmark에서 알러지·목표 hard constraint 위반 0건을 배포 조건으로 둔다.

### 확정된 알러지 계약 (2026-06-22)

- **등록 경계**: 알러지는 `ALLERGY + ALLERGEN_TAG`만 허용하고 알러지·기피 설정 화면을 분리한다. 나머지 기피 정책은 현행을 유지한다.
- **판정 모드**: 알러지가 있으면 항상 verified-only다. Strict 토글은 제거하고 호환 필드는 무시한다.
- **근거**: 출처별 `CONTAINS/MAY_CONTAIN`을 모두 보존하고 제한 태그와 일치하면 차단한다. `RECIPE_DERIVED`는 양성 차단에만 사용한다.
- **프로필**: 검토 태그 집합·표준 버전·출처·유효기간을 가진다. 근거 0개 완결 프로필도 허용하며 제품 변경·만료·충돌은 fail-closed로 회수한다.
- **운영**: 알러젠 유형별 재검증 하위 큐, 태그별 benchmark 활성화, 근거 출처·검토일 표시를 도입한다.
- **기록 전환**: 일반 기록 API는 유지하고 추천→기록 전용 API에서 현재 제한·근거를 재검증한다.
- **보관**: 스냅샷에 정책·프로필·근거 버전을 저장하고 사용자 연결 원본은 90일 보관한다.
- **후속 범위**: 자유 입력 알러지·심각도는 제공하지 않으며 글루텐 프리 등은 `DIETARY_REQUIREMENT`로 분리한다.
