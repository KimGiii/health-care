# Gainsy 포트폴리오

> 운동, 식단, 신체 변화를 한 곳에서 기록하고 목표 달성 과정을 주간 회고로 이어 주는 iOS 헬스 트래킹 서비스

## 1. 프로젝트 요약

Gainsy는 체중 감량, 근육 증가, 체형 개선처럼 명확한 신체 변화 목표를 가진 사용자가 운동과 식단, 신체 측정, 진행 사진을 한 흐름 안에서 기록하고 해석할 수 있도록 만든 헬스케어 앱이다.

기존 운동 앱은 식단 맥락이 약하고, 식단 앱은 운동 성과와 체형 변화를 함께 보기 어렵다는 문제에서 출발했다. Gainsy는 `목표 설정 -> 운동/식단 기록 -> 신체 변화 기록 -> 변화 분석 -> 주간 회고`로 이어지는 기록 루프를 중심에 두고, 사용자가 "오늘 무엇을 했는지"뿐 아니라 "그 행동이 목표에 어떤 의미가 있는지"까지 이해하도록 돕는다.

| 항목 | 내용 |
|---|---|
| 프로젝트 유형 | 개인 풀스택 프로젝트 |
| 진행 기간 | 2026.04 ~ 현재 |
| 서비스 상태 | App Store 출시 및 운영 API 구성, v1.1.1 릴리즈 노트 관리 |
| 담당 범위 | 제품 기획, iOS 앱, 백엔드 API, 데이터 모델링, AWS 인프라, App Store 대응 |
| 핵심 사용자 | 주 2~5회 운동하며 식단과 신체 변화를 함께 관리하려는 사용자 |
| 운영 API | `https://api.gainsy.site` |

## 2. 한 줄 소개

운동과 식단 기록을 신체 변화, 목표 진행률, 주간 회고와 연결해 사용자가 자신의 변화 방향을 이해하고 다음 행동을 결정하게 돕는 iOS 기반 건강 기록 서비스다.

## 4. 문제 정의

헬스 기록 서비스는 많지만, 사용자가 매일 마주하는 문제는 단순한 기록 기능의 부재가 아니었다.

- 운동과 식단을 각각 기록해도 신체 변화와의 연결을 이해하기 어렵다.
- 기록이 쌓여도 목표 대비 상태를 해석해 주는 피드백이 약하다.
- 반복 입력이 번거로워 초반 몇 주 안에 기록 루프가 끊어진다.
- 체중 숫자만으로는 변화 과정을 체감하기 어렵고, 사진과 회고가 함께 필요하다.
- 건강/영양 정보는 사용자 신뢰가 중요하므로 출처, 추정 여부, 제한 사항을 숨기면 안 된다.

Gainsy는 이 문제를 "기록 앱"이 아니라 "목표 달성 과정을 설명하는 기록 시스템"으로 풀었다.

## 5. 핵심 기능

### 목표 기반 홈 대시보드

홈 화면은 오늘의 기록 현황, 주간 진행률, 연속 기록, 영양 목표, 최근 변화 요약을 한눈에 보여준다. 사용자는 앱을 열자마자 오늘 필요한 행동과 현재 목표 대비 위치를 파악할 수 있다.

### 운동 기록

근력, 유산소, 기타 운동 세션을 기록하고 운동 종목별 세트, 반복 횟수, 무게, 시간, 메모를 저장한다. 운동 카탈로그와 사용자 커스텀 운동을 지원하며, 자주 사용하는 운동이 검색에서 더 쉽게 노출되도록 사용 빈도 기반 정렬을 적용했다.

### 식단 기록과 AI 사진 분석

공공 식품 데이터, 브랜드 공식 메뉴, 사용자 커스텀 식품을 기반으로 식단을 기록한다. 식사 사진을 업로드하면 OpenAI Vision 모델을 통해 음식 후보와 영양 추정 초안을 만들고, 사용자가 확인 후 저장하는 방식으로 기록 피로를 줄였다. AI 추정값은 확정값처럼 보이지 않도록 추정 여부와 안내 문구를 함께 제공한다.

### 신체 측정과 진행 사진

체중, 체지방률, 근육량 등 신체 지표를 날짜별로 기록하고 추세를 확인할 수 있다. 진행 사진은 S3 Presigned URL로 업로드하며, 서버에서 EXIF 제거와 썸네일 생성을 처리해 개인정보 노출 위험을 줄였다.

### 목표 기반 식단 추천

이미 섭취한 식단을 차감한 **남은 일일 영양량과 남은 끼니**를 함께 고려해 추천 식단을 만든다. 목표 유형(체중 감량·체형 개선·근육량 증가·지구력·건강 유지)별로 비대칭 영양 제약(hard constraint)을 적용하고, 등록한 알러지·기피 조건은 추천 품질보다 우선해 안전하게 제외한다. 약 50만 건 규모의 검색·기록 카탈로그를 그대로 쓰지 않고 검증된 후보와 현실적인 제공량만 추천에 투입하며, 추천이 실패하면 조건을 조용히 완화하지 않고 실패 사유를 구조화해 노출한다.

### 목표와 주간 회고

체중 감량, 근육 증가, 체성분, 지구력, 일반 건강 목표를 설정하고 진행률을 추적한다. 목표 체크포인트와 주간 회고를 통해 "무엇을 잘했고 다음 주에 무엇을 조정할지"를 정리하도록 설계했다.

### 알림과 출시 대응

Firebase FCM으로 주간 요약 알림을 발송할 수 있는 구조를 갖췄고, App Store 심사 대응을 위해 의료 출처 안내, ATT 사전 설명 화면, 개인정보 처리방침/이용약관 링크, 만 14세 미만 가입 제한을 반영했다.

백엔드는 사용자, 인증, 운동, 식단, 신체 측정, 목표, 인사이트 도메인을 분리했다. 컨트롤러는 인증된 사용자 식별자를 `@CurrentUserId`로만 받도록 통일해 토큰 검증 우회를 막았고, 서비스 계층에서 사용자 소유권 검증과 도메인 규칙을 처리한다.

iOS 앱은 기능 단위로 `Features`를 나누고, 네트워크와 인증 상태는 `Core`에 모았다. 토큰 만료 30초 전 선제 갱신, 401 응답 시 1회 재시도, 동시 호출 시 단일 refresh 보장을 통해 Access Token TTL을 1시간으로 줄여도 사용자 경험이 깨지지 않도록 했다.

## 8. 주요 구현 사례

### 8.1 인증 보안 개선

초기 백엔드에는 일부 컨트롤러가 JWT를 직접 파싱하는 문제가 있었다. `JwtAuthenticationFilter`가 이미 검증한 인증 컨텍스트와 컨트롤러의 직접 파싱 경로가 분리되면 만료/조작 토큰 검증 우회 위험이 생긴다.

이를 해결하기 위해 `@CurrentUserId` 어노테이션과 `CurrentUserIdArgumentResolver`를 도입했다. 이후 컨트롤러는 토큰 문자열을 직접 다루지 않고, Spring Security가 검증한 사용자 ID만 전달받는다. 컨트롤러 테스트도 인증 컨텍스트 주입 방식으로 마이그레이션했다.

### 8.2 읽기 API의 숨은 쓰기 제거

목표 진행률 조회 API가 누락된 목표 체크포인트를 보정하면서 DB 쓰기를 수행하던 문제가 있었다. GET 요청이 쓰기를 포함하면 동시 요청에서 중복 INSERT와 트랜잭션 경합이 발생할 수 있다.

조회 API는 `readOnly`로 유지하고, 누락 체크포인트 보정은 KST 기준 매일 새벽 실행되는 `GoalCheckpointScheduler`로 분리했다. 목표별 try/catch와 별도 트랜잭션을 적용해 한 사용자의 실패가 전체 배치에 전파되지 않도록 했다.

### 8.3 사진 업로드 개인정보 보호

진행 사진은 민감도가 높은 개인 데이터이므로 데이터베이스 BLOB 저장을 피하고 S3 기반 업로드로 설계했다. 서버는 사용자별 prefix를 검증하고 Presigned URL을 발급한다. 업로드 후에는 EXIF 제거와 썸네일 생성을 수행해 위치 정보나 기기 정보가 노출될 가능성을 줄였다.

### 8.4 식품 카탈로그와 추천 신뢰도

식단 기록은 검색 품질이 낮으면 바로 이탈로 이어진다. 공공 식품 데이터와 브랜드 공식 메뉴 CSV를 식품 카탈로그로 적재하고, `source + foodCode` 기준의 동일성 규칙으로 중복을 관리했다.

추천 식단 확장에서는 알러지/기피 식품 회피를 추천 품질보다 우선하는 정책을 설계했다. 알러젠 정보는 `DIRECT_VERIFIED`, `LABEL_DERIVED`, `RECIPE_DERIVED`, `UNKNOWN` 같은 신뢰 레벨로 구분하고, 기본 모드와 Strict 모드를 나눠 사용자가 불확실성을 이해할 수 있도록 했다.

### 8.5 목표 인지 식단 추천 엔진

초기 추천은 카테고리 greedy 선택 후 사후 검증 방식이라, 하루 목표 전체를 기준으로 후보를 고르고 알러지·영양 제약은 뒤에서 검사하는 구조였다. 이 방식은 안전 위반을 사후에 걸러야 하고, "이미 먹은 식단"과 "오늘 남은 끼니"를 반영하지 못했다. 이를 5단계 실행 계획(전역 ADR-0002)에 따라 다음과 같이 재설계했다.

- **남은 영양량 공동 최적화**: 하루 목표가 아니라 이미 섭취한 영양을 차감한 남은 일일 영양량과 남은 끼니를 함께 최적화한다. 후보를 먼저 축소한 뒤 제약 최적화로 feasible 해를 생성해, greedy 선택 후 검증하던 구조를 바꿨다.
- **목표별 비대칭 제약**: 목표 유형마다 열량·단백질·탄수화물·지방의 상·하한을 hard/soft로 구분해 정책 버전(`2026-06-18.v1`)으로 관리하고, 임계값을 구현 상수로 흩뜨리지 않았다.
- **안전 우선·실패 비은닉**: 알러지 등록 사용자는 완결 프로필 검증을 통과한 후보만 추천에 포함되도록 `AllergenSafetyGate`로 게이트를 통합했다. 추천이 불가능하면 조건을 조용히 완화하지 않고 구조화된 실패 응답과 대안 식단을 함께 제공한다.
- **스냅샷과 피드백 루프**: 추천 시점의 입력·결과를 `RecommendationSnapshot`으로 저장하고 기록·재추천 이벤트를 연결해, 최근 7일 반복 기피 같은 개인 선호 점수와 순위 품질 개선의 근거로 사용한다.
- **검증 풀 지속 개선**: source 사실이 유의미하게 바뀌면(매크로·제공량·주의 영양소 상대 5% 초과) 추천 후보 자격을 자동 회수하고, 자동 회수·신선도 만료 항목을 사유·커버리지 가중치 기준으로 모은 운영자용 재검증 큐 API를 제공한다.

품질은 단위·통합 테스트에 더해 고정 시나리오 benchmark(v1, 6 시나리오)로 배포 게이트 baseline을 잡아, 정책·엔진 변경을 baseline 비교와 함께 승격하도록 했다.

### 8.5 App Store 심사 대응

헬스케어 앱은 기능 구현만으로 출시할 수 없다. App Store 심사에서 의료 정보 출처, HealthKit 식별, ATT 권한 요청 흐름 같은 요구사항을 점검했고, 다음 항목을 반영했다.

- 의료 출처 안내 화면 추가
- HealthKit 미사용 키 제거
- ATT 사전 설명 화면 추가
- PrivacyInfo.xcprivacy와 Privacy Labels 정리
- 이용약관/개인정보 처리방침 링크 제공
- 만 14세 미만 가입 제한

테스트는 인증, 식단 기록, 운동 세션, 목표, 인사이트, 알림, 외부 식품 데이터 적재 등 도메인별 단위/컨트롤러 테스트를 중심으로 구성했다. iOS는 ViewModel 단위 테스트와 핵심 흐름 UI 테스트를 분리해 관리한다.

운영 품질 측면에서는 보안 코드 리뷰 회고를 따로 남기고, CRITICAL 2건과 HIGH 5건을 해결했다. 특히 CORS 기본 와일드카드 제거, JWT Secret 기본값 제거, 페이징 size 상한, 외부 HTTP 호출과 DB 트랜잭션 분리, 보안 헤더 적용을 통해 출시 전 위험을 줄였다.

## 10. 제품 설계 원칙

### 기록 피로를 줄인다

사용자는 완벽한 기록보다 빠르게 다시 이어 갈 수 있는 기록을 원한다. 따라서 최근 기록 재사용, 사용 빈도 기반 검색, 사진 기반 식단 초안, 홈 CTA를 통해 기록 시작 비용을 낮췄다.

### 데이터의 한계를 숨기지 않는다

AI 식단 분석, 알러젠 회피, 칼로리 계산은 모두 추정과 한계가 있다. Gainsy는 "정답"처럼 말하기보다 추정 여부, 출처, 주의 문구, 의료 정보 고지를 함께 제공하는 방향으로 설계했다.

### 해석 가능한 피드백을 준다

단순 그래프보다 사용자가 다음 행동을 결정할 수 있는 요약이 중요하다. 목표 대비 진행률, 주간 변화, 기록 빈도, 영양 목표 달성률을 회고와 연결해 행동 조정으로 이어지게 했다.

## 11. 배운 점

- 헬스케어 앱은 기능보다 신뢰 설계가 더 중요하다. 의료적 단정 표현, 개인정보, 출처 고지, 추정값 표시를 제품 구조 안에 넣어야 한다.
- 짧은 JWT TTL은 백엔드 보안만의 문제가 아니라 iOS 네트워크 계층의 동시성 제어와 함께 설계해야 사용자 경험이 유지된다.
- GET API에 숨어 있는 쓰기는 나중에 운영 안정성 문제로 커질 수 있다. 읽기와 쓰기의 책임을 초기에 분리하는 것이 중요하다.
- App Store 출시 과정은 개발의 부가 작업이 아니라 제품 요구사항의 일부다. Privacy Labels, ATT, 의료 출처, 계정 삭제는 초기 설계에 포함되어야 한다.
- 식단 추천은 "맛있고 정확한 추천"보다 "먹으면 안 되는 것을 안전하게 제외하고, 불확실성을 설명하는 것"이 먼저다.

## 12. 앞으로의 개선 방향

- Redis 기반 rate limiting으로 멀티 인스턴스 운영 대비
- iOS 핵심 기록 플로우 UI 테스트 확대
- AWS Secrets Manager 또는 SSM Parameter Store로 운영 시크릿 이관
- 식단 추천 benchmark shadow run과 단계적 정책 승격(Phase 5 Unit 3~4)
- 온라인 지표 기반 추천 순위 가중치 자동 조정
- 식품 카탈로그 중복 관리와 브랜드 공식 메뉴 데이터 확장
- 진행 사진 비교 UX와 실패 재시도 UX 개선

## 13. 이력서용 요약

Gainsy는 운동, 식단, 신체 측정, 진행 사진, 목표, 주간 회고를 하나의 루프로 연결한 iOS 헬스 트래킹 앱이다. SwiftUI 기반 iOS 앱과 Java 21/Spring Boot 백엔드, PostgreSQL/Redis/S3/FCM/OpenAI, AWS/Terraform 운영 인프라를 end-to-end로 구현했다. JWT 인증, Presigned URL 기반 사진 업로드, AI 식단 사진 분석, 목표 체크포인트 스케줄링, App Store 심사 대응까지 제품 출시 과정 전반을 경험했다. 특히 알러지 안전을 우선하고 남은 영양량을 공동 최적화하는 목표 인지 식단 추천 엔진을 제약 최적화·검증 풀·스냅샷 피드백·고정 시나리오 benchmark까지 단계적으로 설계했다. 보안 코드 리뷰를 통해 JWT 검증 경로 통합, CORS 강화, 토큰 TTL 단축, 페이징 제한, 읽기 API 사이드이펙트 제거 등 운영 리스크를 개선했다.
