## 잘 된 것 (Good)

- **검색·기록·추천의 기준 데이터를 하나로 모음**: 런타임 외부 API 호출을 제거하고 내부 `food_catalog`를 공통 기반으로 삼아 지연과 장애, 결과 비영속 문제를 줄였다.
- **안전 조건을 타입과 조회 경계에 배치**: 알러젠 신뢰도, 추천 상태, 큐레이션 규칙을 후처리 문구가 아니라 DB 필터와 도메인 타입으로 끌어올렸다.
- **운영 경로와 사용자 경로를 분리**: 공공데이터와 브랜드 메뉴 수집은 관리자·배치 경로로 옮기고 사용자 요청은 검증된 내부 데이터만 읽도록 구조를 명확히 했다.
- **위젯을 제품 행동으로 연결**: 단순 수치 표시를 넘어 목표 화면 라우팅까지 붙여 기록과 목표 확인의 거리를 줄였다.

## 아쉬운 것 (Bad)

- **공공데이터 응답 계약을 다시 수정함**: 식품영양성분DB API가 예상한 중첩 구조가 아니라 flat body와 integer 페이지네이션을 사용해 후속 수정이 필요했다.
- **추천 구현 직후 구조 리팩터링이 연속됨**: 서비스→use case, 팩토리, sealed type, DB 필터 전환이 같은 주에 이어졌다. 초기 도메인 경계를 조금 더 먼저 잡았으면 변경 폭을 줄일 수 있었다.
- **추천 가능성과 검색 가능성의 데이터 품질 차이가 큼**: 카탈로그 수가 늘어도 알러젠 근거와 영양값이 검증되지 않은 항목은 추천할 수 없다. 총 데이터 건수가 곧 추천 품질은 아니었다.
- **위젯의 다중 목표 정책이 미정**: 단일 목표 가정으로 먼저 구현해 여러 ACTIVE 목표에서 어떤 목표를 표시할지 후속 설계가 필요해졌다.

## 배운 것 (Learned)

- **외부 데이터는 먼저 저장하고 검증한 뒤 제공해야 한다**: 사용자 요청 중 외부 API를 호출하면 가용성과 재현성을 통제하기 어렵다. 배치 적재, 원본 식별자, 데이터 버전이 운영의 기본 단위가 된다.
- **알러젠 안전은 포함 태그 목록만으로 증명되지 않는다**: 알러젠이 없다는 결론도 검증된 완결 프로필이 필요하다. 근거가 없는 0건과 검증 결과 0건을 구분해야 한다.
- **추천 후보 수보다 자격 계약이 중요하다**: `SEARCH_ONLY`, `RECOMMENDABLE`, `RECOMMENDABLE_WITH_CAUTION`, `DISABLED`를 구분해야 검색 편의와 추천 안전을 동시에 유지할 수 있다.
- **WidgetKit의 단순 스냅샷도 도메인 정책을 드러낸다**: 여러 활성 목표를 허용한다면 위젯 선택, 캐시 버전, deep link 대상까지 함께 설계해야 한다.
