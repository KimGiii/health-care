# FatSecret Platform API 약관 검토 메모

작성일: 2026-06-09  
원문 기준: 사용자가 첨부한 `fatsecret Platform API Terms of Use` 전문  
대상 독자: 기획, 백엔드, iOS, 법무 검토 담당자

---

## 1. 목적

FatSecret Platform API를 식품 검색, 식단 기록, 식단 추천, 내부 식품 카탈로그 보강에 사용할 수 있는지 판단하기 위해 약관상 제품·기술 제약을 정리한다.

이 문서는 법률 자문이 아니라 제품/기술 의사결정을 위한 1차 검토 메모다. 실제 계약, 배포, 과금, 데이터 저장 정책 확정 전에는 FatSecret 공식 약관 최신본과 별도 계약 가능성을 다시 확인해야 한다.

## 2. 1차 결론

현재 약관만 기준으로 보면 FatSecret Platform API는 우리 서비스의 `food_catalog` 장기 보강 소스나 식단 추천 엔진의 핵심 데이터 소스로 쓰기 어렵다.

주요 이유는 다음과 같다.

- API Content는 명시적으로 무기한 저장 가능하다고 표시된 경우가 아니면 획득 후 24시간 안에 삭제하거나 다시 요청해서 교체해야 한다.
- FatSecret Platform API를 식단, 영양, 건강 조언·가이드·진단 제공 목적으로 사용하면 안 된다고 명시되어 있다.
- 우리 서비스는 식단 기록과 목표 달성 과정을 다루며, 이미 식단 추천/제한 기능을 포함하고 있어 의료·영양 조언으로 해석될 수 있는 화면과 API가 존재한다.
- Content를 표시하는 모든 화면에서 FatSecret 출처 표기가 필요하며, 사용자 약관에도 FatSecret 약관 링크와 동의 문구가 필요하다.
- 일일 호출 제한은 애플리케이션 기준 5,000 calls/day이며, 우회성 호출 분산은 약관 위반으로 볼 수 있다.

따라서 별도 서면 허가나 명확한 저장 가능 Content 범위가 확보되기 전까지는 `검색 보조 PoC` 또는 `단기 표시용 외부 검색` 정도로만 검토하는 것이 안전하다.

## 3. 약관상 핵심 제약

### 3.1 계정과 키 관리

- FatSecret Platform API 계정을 생성해야 하며, 이메일당 계정 생성 제한이 있을 수 있다.
- 발급받은 Key, secret, token, password 등은 제3자에게 판매, 이전, 재라이선스, 공개할 수 없다.
- Key는 최초 신청한 애플리케이션 외 다른 애플리케이션에 사용할 수 없다.
- Key로 발생한 모든 활동은 계정 보유자가 책임진다.

제품/기술 영향:

- API Key는 iOS 앱에 포함하지 않고 백엔드 서버에서만 보관해야 한다.
- 운영 환경별 Key 사용 범위와 애플리케이션 등록 정보를 분리해야 한다.
- 로그, crash report, analytics에 Key가 노출되지 않도록 마스킹해야 한다.

### 3.2 애플리케이션 공개 접근성

- 애플리케이션은 일반 사용자가 접근 가능해야 한다.
- 별도 계약 또는 서면 허가 없이 방화벽 뒤나 내부 네트워크 전용으로만 운영하면 안 된다.
- 개발/테스트 단계의 내부 사용은 예외로 허용된다.

제품/기술 영향:

- 운영 배포 전 FatSecret 측 애플리케이션 등록 정보와 실제 공개 서비스 URL이 일치해야 한다.
- 내부 관리자 도구나 비공개 배치 전용으로만 API를 쓰는 방식은 별도 허가가 필요할 수 있다.

### 3.3 출처 표기

- FatSecret Content가 제공되거나 표시되는 모든 위치에서 FatSecret이 출처임을 명확히 표시해야 한다.
- Content에 포함된 저작권, 상표, 권리 고지를 제거하면 안 된다.
- Attribution link는 FatSecret API 사용 중단 여부와 무관하게 유지해야 한다고 해석되는 문구가 있다.

제품/기술 영향:

- iOS 검색 결과, 식단 기록 상세, 가져온 식품 상세, 웹/랜딩 페이지 등 FatSecret Content가 보이는 모든 화면에 출처 표기가 필요하다.
- 백엔드 응답 DTO에 `source`, `sourceDisplayName`, `sourceUrl`, `attributionRequired` 같은 메타데이터가 필요하다.
- 내부 `food_catalog`에 FatSecret 유래 데이터를 넣는다면 출처와 attribution 보존이 필수다. 단, 저장 가능성 제약 때문에 이 방식은 별도 검토 전까지 보류해야 한다.

### 3.4 호출 제한

- 약관에 명시된 호출 제한은 애플리케이션당 5,000 calls/day다.
- 사용하지 않은 호출량은 다음 날로 이월되지 않는다.
- 프로그램적으로 rate limit을 우회하려는 방식은 약관 위반으로 본다.

제품/기술 영향:

- 사용자 검색 입력마다 즉시 API를 호출하는 방식은 위험하다.
- 서버 측 rate limit, debounce, 요청 deduplication, 장애 시 fallback이 필요하다.
- 운영 모니터링에서 FatSecret 일일 호출량을 별도 지표로 추적해야 한다.

### 3.5 Content 저장 제한

- 명시적으로 무기한 저장 가능하다고 식별된 Content가 아니면 획득 후 24시간 안에 삭제하거나 다시 요청해서 교체해야 한다.
- 무기한 저장 가능 Content라도 FatSecret이 그 식별을 중단하거나 라이선스가 종료되면 삭제 또는 교체해야 한다.

제품/기술 영향:

- FatSecret 데이터를 내부 `food_catalog`에 장기 저장하는 것은 기본적으로 부적합하다.
- FatSecret 응답을 식단 기록 영구 데이터로 저장하는 것도 Content 저장에 해당할 수 있으므로 위험하다.
- 캐시는 최대 24시간 TTL을 기본으로 잡아야 하며, Content 원본과 파생 필드의 저장 여부를 구분해야 한다.
- 사용자 기록에 남길 데이터가 FatSecret Content인지, 사용자가 직접 입력한 데이터인지, 내부 계산 결과인지 법무/정책 기준이 필요하다.

### 3.6 사용자 약관 연결

애플리케이션에서 FatSecret Content를 다른 사용자에게 보여주는 경우 다음이 필요하다.

- 앱 사용자에게 FatSecret API Terms of Use 링크를 표시한다.
- 우리 앱 약관에 사용자가 우리 앱을 사용함으로써 FatSecret 약관에도 구속된다는 취지의 문구를 넣는다.
- 사용자 개인정보와 법적 권리를 보호한다.

제품/기술 영향:

- `docs/legal/terms.html`, 앱 내 약관/동의 화면, 회원가입 동의 플로우를 수정해야 할 수 있다.
- 이미 가입한 사용자에게 약관 변경 재동의를 받아야 하는지 별도 정책 판단이 필요하다.

### 3.7 건강·영양 조언 제한

- FatSecret Platform API를 식단, 영양, 건강 조언·가이드·진단 제공 목적으로 사용하면 안 된다.
- API로 생성된 정보가 의사 상담, 평가, 치료를 대체하지 않는다는 점을 명확히 해야 한다.

제품/기술 영향:

- 우리 서비스의 식단 추천, 알레르기/제한, 목표 기반 추천 문구와 직접 충돌할 수 있다.
- FatSecret Content를 추천 엔진의 후보 풀, 점수 계산, “이 음식을 드세요”류 UX에 사용하는 것은 별도 허가 없이는 보류해야 한다.
- 단순 검색/기록 화면에서도 의료 대체가 아니라는 안내 문구가 필요하다.

### 3.8 과도한 사용과 모니터링

- Content를 과도하게 수집, 색인, 크롤링하는 방식은 금지된다.
- FatSecret은 준수 여부 확인을 위해 애플리케이션 접근을 요청하거나 크롤링/모니터링할 수 있으며, 이를 방해하면 안 된다.

제품/기술 영향:

- 대량 식품 카탈로그 enrichment batch는 약관상 위험하다.
- public-facing 화면의 attribution과 약관 링크가 외부에서도 확인 가능해야 한다.

## 4. 우리 서비스 기능별 적합성

| 사용 시나리오 | 적합성 | 판단 |
|---|---|---|
| 사용자가 식품명을 검색할 때 외부 결과를 임시 표시 | 제한적 가능 | 출처 표기, 24시간 캐시, rate limit, 약관 동의가 필요하다. |
| 선택한 FatSecret 식품을 내부 `food_catalog`에 영구 import | 부적합 | 저장 가능 Content 범위가 명확하지 않으면 24시간 삭제/교체 의무와 충돌한다. |
| FatSecret 영양값을 사용자의 식단 기록에 장기 저장 | 고위험 | 기록 데이터가 Content 저장으로 해석될 수 있어 별도 법무 검토가 필요하다. |
| 식단 추천 후보 풀로 사용 | 부적합 | 약관의 식단/영양/건강 조언 제한과 직접 충돌할 수 있다. |
| 관리자 배치로 대량 수집해 카탈로그 보강 | 부적합 | 과도한 수집, 색인, 저장 제한에 걸릴 가능성이 높다. |
| 내부 PoC에서 API 응답 품질만 비교 | 가능 | 개발/테스트 범위, Key 관리, 데이터 폐기 기준을 지켜야 한다. |

## 5. 도입하려면 필요한 최소 안전장치

FatSecret API를 PoC 이상으로 사용하려면 아래 항목을 먼저 충족해야 한다.

1. 공식 최신 약관 URL, Attribution Policy, 저장 가능 Content 범위 확인
2. 별도 서면 허가 또는 유료 계약으로 장기 저장/추천 사용 가능 여부 확인
3. API Key 서버 보관 및 운영 환경별 분리
4. 서버 측 호출량 제한, 24시간 이하 캐시 TTL, 장애 fallback
5. FatSecret Content 표시 화면의 attribution UI
6. 앱 약관/개인정보/동의 플로우에 FatSecret 약관 링크와 고지 반영
7. 의료·영양 조언이 아니라는 disclaimer 반영
8. 추천 엔진과 FatSecret Content 사이의 데이터 경계 정의
9. Content 삭제/교체 작업을 감사 가능한 방식으로 기록
10. FatSecret이 애플리케이션 준수 여부를 확인할 수 있는 접근 경로 준비

## 6. 권장 의사결정

MVP와 현재 식품 카탈로그 강화 계획에서는 FatSecret을 핵심 소스로 채택하지 않는다.

우선순위는 기존 계획대로 다음 순서를 유지한다.

1. 공공데이터 기반 내부 카탈로그 강화
2. 브랜드 공식 영양정보의 관리자 검수 CSV 적재
3. 사용자 커스텀 식품 입력 품질 개선
4. 외부 API는 검색 품질 비교 PoC로만 제한

FatSecret을 다시 검토할 조건은 다음과 같다.

- Content 장기 저장 가능 범위가 공식적으로 확인됨
- 식단 추천/영양 안내 목적 사용에 대한 별도 허가가 확보됨
- Attribution Policy를 iOS UX와 약관에 반영할 수 있음
- 일일 5,000 calls/day 제한 안에서 사용자 경험이 유지됨

## 7. 후속 작업 후보

- `docs/FOOD_CATALOG_GUIDE.md`에 FatSecret을 “보류된 외부 API 후보”로 추가한다.
- 식품 외부 API 후보 비교표를 별도 문서로 만들고 공공데이터, 브랜드 CSV, FatSecret, Nutritionix를 같은 기준으로 비교한다.
- `docs/legal/terms.html`에 외부 영양정보 제공자 연동 시 필요한 고지 블록 초안을 추가한다.
- 백엔드 외부 식품 검색 추상화에 `storableUntil`, `attribution`, `sourceTermsUrl` 필드를 포함할지 검토한다.
