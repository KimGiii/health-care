# Project Memory

작성일: 2026-06-18

이 문서는 대화 세션이 바뀌어도 유지해야 하는 확정 제품 결정을 짧게 기록한다. 상세 근거와 구현 순서는 연결된 PRD·ADR·실행 계획을 따른다.

## 현재 제품 방향

Gainsy 식단 추천의 차별점은 완결된 메뉴나 레시피를 생성하는 것이 아니라, **알러지·기피 조건을 위반하지 않으면서 사용자의 신체 목표와 남은 일일 영양량을 정밀하게 맞추는 것**이다.

## 확정 결정

1. 알러지와 사용자가 명시한 기피 조건은 hard constraint다. 조건을 조용히 완화한 근접 식단은 추천으로 노출하지 않는다.
2. 알러지 사용자의 추천 후보는 완결된 알러젠 프로필이 `DIRECT_VERIFIED` 또는 `LABEL_DERIVED` 근거로 검증된 식품으로 제한한다. 추론·일반 레시피·AI 결과는 검수 후보 생성에만 사용한다.
3. 의료적 안전을 보증하지 않는다. 교차오염, 매장별 원재료 변경, 실제 제품 차이는 섭취 전 라벨 확인 대상으로 안내한다.
4. 추천 목적함수는 목표 유형별로 다르다. 체중 감량·체형 개선은 열량 상한 미만, 근육량 증가는 단백질 하한 이상을 절대 제약으로 둔다. 지구력·건강 유지도 별도 정책을 가진다.
5. 목표 기간은 희망 일정이다. 권장 범위를 벗어나면 열량을 무리하게 조정하지 않고 달성 가능한 예상 날짜를 제안한다.
6. 목표 열량과 예상 달성일은 일일 체중이 아니라 주간 추세로 조정한다. 하루 실패분을 다음 날 과도하게 보상하지 않는다.
7. 추천 전 이미 기록한 식단을 고정하고, 남은 영양량과 남은 끼니 전체를 공동 최적화한다. 새 식단 기록 후에는 남은 끼니를 다시 계산한다.
8. 운동 소모 열량은 식사 예산에 1:1로 더하지 않는다. 목표별 회복 영양 배분을 위한 제한적 신호로만 사용한다.
9. 감량·체형 개선의 열량 상한에는 영양값과 제공량의 불확실성 버퍼를 둔다. 미검증 섭취 기록은 열량 상한·단백질 하한을 보수적으로 반영한다.
10. 추천 엔진은 임의 g을 만들지 않고 검증된 이산 제공량을 사용한다. 식단 기록하기 화면은 제공량 프리셋을 기본으로 제공하되 직접 g 입력을 유지한다.
11. 하루 영양 목표는 hard constraint, 끼니별 열량·단백질 분배는 soft constraint다.
12. 50만 건 전체를 추천 풀로 쓰지 않는다. 검색·기록 카탈로그와 검증된 추천 풀을 분리하고, 추천 실패를 가장 많이 줄이는 식품부터 검증한다.
13. 중복 식품은 삭제하지 않고 canonical 그룹으로 묶는다. 추천·선호·통계는 그룹 기준으로 집계하며 불확실한 그룹에는 알러젠 검증을 전파하지 않는다.
14. 영양값 누락을 0으로 해석하지 않는다. 목표별 필수 영양 데이터 완전성에 따라 추천 자격을 계산한다.
15. greedy 엔진은 단계적으로 제약 최적화 엔진으로 교체한다. hard constraint를 만족하는 상위 해를 생성한 뒤 반복·선호·다양성으로 순위를 정한다.
16. 추천 스냅샷과 노출·재추천·기록 전환·삭제/교체 이벤트를 저장한다. 재추천 이유는 선택형 원탭 피드백으로 수집한다.
17. 사용자 연결 개인화 이력은 기본 90일 보관하고, 장기 품질 분석에는 비식별 집계만 사용한다. 자유 입력 기피 키워드 원문은 분석 이벤트에 저장하지 않는다.
18. 새 데이터와 엔진은 고정 benchmark를 통과해야 한다. 알러지 또는 목표별 hard constraint 위반은 배포 차단 조건이다.
19. 추천 실패 시 일반 오류가 아니라 불가능한 제약과 조정 가능한 선택지를 설명한다.
20. 구현은 단계적으로 진행한다: 정책·benchmark → 데이터 계약 → 제약 최적화 → 이벤트·피드백 → 운영 데이터 기반 개선.

## 현재 구현과의 중요한 차이

- Phase 1의 목표별 정책, 남은 영양량·불확실성, 목표일 주간 재계산 계약과 greedy benchmark는 구현됐다. 아직 운영 `DailyDietRecommendationUseCases`에는 연결하지 않았다.
- 현행 기본 알러지 모드는 미검증 후보를 통과시킬 수 있다. 후속 정책에서는 알러지 등록 사용자의 verified-only 게이트가 기본이다.
- 현행 엔진은 칼로리 중심 greedy 선택과 사후 검증을 사용한다. 후속 엔진은 목표별 비대칭 hard constraint와 남은 하루 공동 최적화를 사용한다.
- 현행 추천 결과는 영속화하지 않는다. 후속 정책은 식단 계획 도메인이 아니라 최소 추천 스냅샷·이벤트를 저장한다.
- 현행 제공량은 25g 단위로 임의 조정한다. 후속 정책은 검증된 제공량 옵션만 추천에 사용한다.
