# Project Memory

작성일: 2026-06-22

이 문서는 대화 세션이 바뀌어도 유지해야 하는 확정 제품 결정을 짧게 기록한다. 상세 근거와 구현 순서는 연결된 PRD·ADR·실행 계획을 따른다.

## 현재 제품 방향

Gainsy 식단 추천의 차별점은 완결된 메뉴나 레시피를 생성하는 것이 아니라, **알러지·기피 조건을 위반하지 않으면서 사용자의 신체 목표와 남은 일일 영양량을 정밀하게 맞추는 것**이다.

## 확정 결정

1. 알러지와 사용자가 명시한 기피 조건은 hard constraint다. 조건을 조용히 완화한 근접 식단은 추천으로 노출하지 않는다.
2. 알러지 사용자의 추천 후보는 완결된 알러젠 프로필이 `DIRECT_VERIFIED` 또는 `LABEL_DERIVED` 근거로 검증된 식품으로 제한한다. 사용자 Strict 토글로 이 기준을 완화하거나 강화하지 않는다.
3. 의료적 안전을 보증하지 않는다. 공식 `MAY_CONTAIN`과 교차접촉 표시는 hard exclusion으로 처리하되, 실제 제품·매장별 변경과 제조 환경 차이는 섭취 전 라벨 확인 대상으로 안내한다.
4. 추천 목적함수는 목표 유형별로 다르다. 체중 감량·체형 개선은 열량 상한 미만, 근육량 증가는 단백질 하한 이상을 절대 제약으로 둔다. 지구력·건강 유지도 별도 정책을 가진다.
5. 목표 기간은 희망 일정이다. 권장 범위를 벗어나면 열량을 무리하게 조정하지 않고 달성 가능한 예상 날짜를 제안한다.
6. 목표 열량과 예상 달성일은 일일 체중이 아니라 주간 추세로 조정한다. 하루 실패분을 다음 날 과도하게 보상하지 않는다.
7. 추천 전 이미 기록한 식단을 고정하고, 남은 영양량과 남은 끼니 전체를 공동 최적화한다. 새 식단 기록 후에는 남은 끼니를 다시 계산한다.
8. 운동 소모 열량은 식사 예산에 1:1로 더하지 않는다. 목표별 회복 영양 배분을 위한 제한적 신호로만 사용한다.
9. 감량·체형 개선의 열량 상한에는 영양값과 제공량의 불확실성 버퍼를 둔다. 미검증 섭취 기록은 열량 상한·단백질 하한을 보수적으로 반영한다.
10. 추천 엔진은 임의 g을 만들지 않고 검증된 이산 제공량을 사용한다. 식단 기록하기 화면은 제공량 프리셋을 기본으로 제공하되 직접 g 입력을 유지한다.
11. 하루 영양 목표는 hard constraint, 끼니별 열량·단백질 분배는 soft constraint다.
12. 50만 건 전체를 추천 풀로 쓰지 않는다. 검색·기록 카탈로그와 검증된 추천 풀을 분리하고, 추천 실패를 가장 많이 줄이는 식품부터 검증한다.
13. 중복 식품은 삭제하지 않고 canonical 그룹으로 묶는다. 추천·선호·통계는 그룹 기준으로 집계하며 불확실한 그룹에는 알러젠 검증을 전파하지 않는다.
14. 영양값 누락을 0으로 해석하지 않는다. 목표별 필수 영양 데이터 완전성에 따라 추천 자격을 계산한다.
15. greedy 엔진은 단계적으로 제약 최적화 엔진으로 교체한다. hard constraint를 만족하는 상위 해를 생성한 뒤 반복·선호·다양성으로 순위를 정한다.
16. 추천 스냅샷과 노출·재추천·기록 전환·삭제/교체 이벤트를 저장한다. 재추천 이유는 선택형 원탭 피드백으로 수집한다.
17. 사용자 연결 개인화 이력은 기본 90일 보관하고, 장기 품질 분석에는 비식별 집계만 사용한다. 자유 입력 기피 키워드 원문은 분석 이벤트에 저장하지 않는다.
18. 새 데이터와 엔진은 고정 benchmark를 통과해야 한다. 알러지 또는 목표별 hard constraint 위반은 배포 차단 조건이다.
19. 추천 실패 시 일반 오류가 아니라 불가능한 제약과 조정 가능한 선택지를 설명한다.
20. 구현은 단계적으로 진행한다: 정책·benchmark → 데이터 계약 → 제약 최적화 → 이벤트·피드백 → 운영 데이터 기반 개선.
21. 알러지는 `ALLERGY + ALLERGEN_TAG`만 허용한다. 알러지와 기피 설정 화면을 분리하고 신규 `AVOID + ALLERGEN_TAG`를 막으며, 나머지 기피 정책은 현행을 유지한다.
22. 알러젠 근거는 출처·버전별 `CONTAINS`와 `MAY_CONTAIN`으로 보존한다. 제한 태그와 일치하는 두 관계는 모두 추천에서 제외한다.
23. `RECIPE_DERIVED`는 포함 알러젠 발견·차단에만 사용하고, 레시피에 태그가 없다는 사실은 통과 근거로 쓰지 않는다.
24. 완결 알러젠 프로필은 검토 태그 집합과 표준 버전을 명시한다. 근거가 0개인 완결 검토도 허용하며, 제품 변경·만료·무효화·근거 충돌은 fail-closed로 추천 자격을 회수한다.
25. 출처별 원본 알러젠 근거는 삭제하지 않는다. 동일 제품의 최신 공식 전체 라벨은 이전 근거를 판정에서 대체할 수 있고, 교차 출처 충돌은 유형별 알러젠 재검증 하위 큐로 보낸다.
26. 지원 목록 밖 자유 입력 알러지와 심각도는 받지 않는다. 알러젠 태그는 데이터 커버리지와 고정 benchmark를 통과한 항목만 정책 버전별로 활성화한다.
27. 추천 스냅샷은 알러지 정책·제한 태그·프로필·근거 버전을 90일 보존한다. 일반 기록 API는 유지하고 추천 끼니 전환만 현재 제한과 근거를 다시 검증한다.
28. 글루텐 프리처럼 검증된 속성을 요구하는 조건은 알러지·기피와 다른 `DIETARY_REQUIREMENT`로 분리하고 별도 후속 작업으로 다룬다.

## 현재 구현과의 중요한 차이

- 목표별 남은 영양량, 제약 최적화 엔진, 검증된 제공량 옵션, 추천 스냅샷·이벤트, canonical 후보 게이트는 운영 추천 경로에 연결됐다.
- 현행 제한 저장과 후보 파서는 `ALLERGY`와 `AVOID` 조합을 충분히 구분하지 않으며 iOS 알러젠 화면도 두 type을 함께 제공한다.
- 현행 `AllergenSafetyGate`는 알러젠 제한에 별도 프로필을 요구하지만 `strictAllergyMode`가 legacy 태그 플래그를 추가 요구한다. 기본/Strict 2모드와 태그 행 기반 완결성은 제거 대상이다.
- 현행 알러젠 태그는 식품·태그당 단일 출처이며 `CONTAINS/MAY_CONTAIN`, 다중 출처 근거, 검토 태그 범위, 근거 충돌을 표현하지 못한다.
- 브랜드 CSV와 관리자 태그 작업은 신규 완결 `FoodAllergenProfile`을 공통 경계에서 원자적으로 생성하지 않는다. 무태그 검증 완료 브랜드 행도 수용하지 못한다.
- 현행 재검증 큐는 영양·제공량 사실 변경과 데이터 만료만 다루며 알러젠 만료·무효화·충돌 하위 큐는 없다.
- 추천 스냅샷은 알러젠 정책·프로필·근거 버전을 보존하지 않고, iOS 추천 기록은 일반 기록 API를 호출해 전환 재검증과 전환 이벤트가 연결되지 않는다.
- 현재 추천 후보 규모에서는 Java 알러젠 게이트를 유지한다. DB 선필터는 검증 풀이 수천 건으로 늘거나 p95 기준을 넘을 때 도입한다.
