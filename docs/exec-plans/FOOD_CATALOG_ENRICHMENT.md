# 식품 데이터(food_catalog) 보강 실행 계획

작성일: 2026-06-04
상태: 계획 초안
대상: 백엔드, 데이터 운영
관련: `docs/product-specs/DIET_RECOMMENDATION_RESTRICTIONS_PRD.md` (추천 기능이 본 카탈로그를 후보 풀로 사용)

> 본 계획은 **AI 추정 기능을 제외하고**, 공공 권위 데이터로 `food_catalog`의 폭(커버리지)과 깊이(필드)를 늘리는 작업을 다룬다.

---

## 1. 배경과 현황 진단

| 항목 | 현황 | 한계 |
|---|---|---|
| 시드 | 글로벌 식품 약 50건 (`V12`) | 한식 커버리지 빈약 |
| 외부 연동 | 식약처 가공식품+일반식품 API를 **검색 시점 실시간 호출** (`PublicFoodApiClientImpl`) | 지연·가용성·트래픽 리스크, 결과 비영속 |
| 필드 | 10종 영양소 + 카테고리 (`FoodCatalog`) | **1회 제공량·출처·식품코드·브랜드·이미지 없음** |
| 임포트 | 사용자 검색→임포트 시 `is_custom=true` (`FoodImportService`) | 개인 단위, 전역 보강 아님 |

핵심 전환 목표: **"실시간 검색 의존 + 50건 시드" → "권위 DB 일괄 적재 + 1회 제공량 보유 + 출처 추적"**.

## 4. 스키마 보강 (Flyway 신규 마이그레이션)

`food_catalog`에 추가할 컬럼 — **실익 있는 것만**(YAGNI):

| 컬럼 | 타입 | 출처 | 용도 |
|---|---|---|---|
| `food_code` | VARCHAR(30) | 식약처 식품코드 | 표준 키 → upsert·중복 제거·갱신 |
| `source` | VARCHAR(30) | 출처 구분 | `MFDS`, `SEED`, `USER_CUSTOM` 등 추적 |
| `serving_size_g` | DOUBLE | 식품중량 | 1회 제공량 |
| `serving_reference` | VARCHAR(50) | 1회섭취 참고량(예: "210g") | 표시·기록 보조 |
| `maker` | VARCHAR(150) | 제조사명 | 가공식품 식별(이미 DTO엔 존재, 영속화) |

```sql
ALTER TABLE food_catalog
  ADD COLUMN food_code        VARCHAR(30),
  ADD COLUMN source           VARCHAR(30) NOT NULL DEFAULT 'SEED',
  ADD COLUMN serving_size_g   DOUBLE PRECISION,
  ADD COLUMN serving_reference VARCHAR(50),
  ADD COLUMN maker            VARCHAR(150);

CREATE UNIQUE INDEX uq_food_catalog_food_code
  ON food_catalog (food_code)
  WHERE food_code IS NOT NULL AND deleted_at IS NULL;
```

**보류 필드**(과적재 방지):
- 미량영양소 24종 전체 → 현재 10종으로 추천 성공기준 충족. 표준데이터 라이선스 확정 시 재검토.
- `image_url` → 메뉴젠 상업 제외로 보류. v2.
- `allergen` → 별도 테이블 `food_allergen_tags`(추천 기능 실행 계획 소관). 본 문서 범위 아님.

## 5. 적재 파이프라인 (배치)

추천 런타임과 분리된 **사전 배치 임포트**로만 외부 데이터를 가져온다(추천 시 외부 호출 금지 — PRD 데이터 운영 원칙과 정합).

1. **수집기** `FoodCatalogBulkImporter` (신규, 스케줄/수동 트리거)
   - 15127578 API를 페이지네이션으로 순회 (개발계정 10,000/일 → 다일 분할 또는 운영계정 신청)
   - 또는 포털 전체 파일(XLS/CSV) 1회 다운로드 후 적재
2. **정규화**
   - 식품명 NFC 정규화·공백 축약(기존 로직 재사용)
   - 대분류 → `FoodCategory` 매핑(기존 `CATEGORY_MAPPING` 재사용)
   - 칼로리 0/결측 행 제외(기존 검증 재사용)
3. **upsert**
   - `food_code` 기준 존재하면 갱신, 없으면 삽입
   - `is_custom=false`, `source='MFDS'`로 적재
   - 사용자 커스텀(`is_custom=true`)은 덮어쓰지 않음
4. **멱등성**: 동일 배치 재실행 시 중복 생성 없이 갱신만(immutable upsert)

운영 주기: 소스가 **분기/연 단위 갱신**이므로 수동 또는 분기 1회 스케줄로 충분.

## 6. 실시간 검색 → fallback 강등

- 현재 `PublicFoodApiClientImpl.search`는 매 검색마다 외부 2개 API 호출.
- 보강 후: **검색은 내부 `food_catalog` 우선**. 내부 결과가 비거나 부족할 때만 외부 API fallback.
- 이로써 일반 검색의 지연·트래픽 의존이 사라지고, 외부 API는 "최신 신제품" 보완 역할만 남는다.

## 8. 구현 순서

1. **(선결) 표준데이터 3종 라이선스 서면 확인** — 상업 이용 가능으로 확인되면 §4 미량영양소 보강 범위 확장 검토. 불가 시 15127578(제한없음)만으로 진행.
2. Flyway 마이그레이션: `food_catalog` 컬럼 보강(§4) + `food_code` 유니크 인덱스
3. `FoodCatalog` 엔티티·DTO에 신규 필드 반영 (불변 패턴 유지)
4. `FoodCatalogBulkImporter` 구현(API 순회 또는 파일 적재) + 정규화/upsert
5. 배치 1회 실행 → 적재 건수·결측·중복 검증
6. 검색 경로를 내부 우선 + 외부 fallback으로 변경(§6)
7. 테스트: 정규화·upsert 멱등성·카테고리 매핑·fallback 분기
8. (선택) 데이터 출처 고지 문구 추가

## 9. 오픈 이슈 / 선결 조건

- **표준데이터 3종(15100065/66/70) 상업 이용 가능 여부 확인** — 라이선스 공란. 소관기관 문의 필요. (블로커: 미량영양소 24종 보강 여부)
- 15127578 API 전체 적재 시 **개발계정 10,000/일 트래픽** — 다일 분할 vs 운영계정 신청 결정.
- 전체 파일 다운로드(포털 5만 건 초과는 파일/API) 경로의 라이선스가 API(제한없음)와 동일한지 확인.
- 적재 후 기존 50건 글로벌 시드(`V12`)와의 중복 처리 정책(식품명 기준 병합 여부).
- 데이터 출처 고지 UI 위치(설정/약관) 결정.
