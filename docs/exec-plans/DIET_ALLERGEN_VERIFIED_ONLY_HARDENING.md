# 식단 추천 verified-only 알러지 계약 강화 실행 계획

작성일: 2026-06-22  
상태: 설계 확정 / 구현 대기  
대상: 백엔드, iOS, 데이터 운영, 제품 분석  
상위 문서: `docs/product-specs/DIET_RECOMMENDATION_RESTRICTIONS_PRD.md`  
전역 ADR: `docs/adr/0005-versioned-allergen-evidence-fail-closed.md`

## 1. 목표와 범위

알러지 등록 사용자의 추천을 버전된 출처 근거와 완결 알러젠 프로필로만 판정하고, 누락·만료·충돌을 통과로 해석하지 않는 fail-closed 계약으로 전환한다.

이번 범위:

- 알러지·기피 UI와 제한 조합 분리
- Strict 사용자 토글 폐기와 API 호환
- 출처별 `CONTAINS`/`MAY_CONTAIN` 근거 보존
- 검토 범위를 가진 완결 프로필
- 원자적 적재·무효화·충돌 처리
- 단계별 후보 진단과 구조화된 실패
- 추천 스냅샷 근거 버전과 추천→기록 재검증
- 알러젠별 benchmark와 단계 출시

이번 범위가 아닌 것:

- 기피 식품 정책 재설계. 기존 `FOOD/CATEGORY/KEYWORD` 동작은 유지한다.
- 글루텐 프리·비건·노출량 같은 `DIETARY_REQUIREMENT` 구현
- 자유 입력 알러지, 알러지 심각도, 의료 진단·치료 기능
- 검증 후보가 작을 때의 DB 알러젠 선필터 최적화

## 2. 현재 구현과 목표의 차이

| 영역 | 현재 구현 | 목표 계약 |
|---|---|---|
| 제한 조합 | `ALLERGY/AVOID`와 네 target 조합을 허용 | `ALLERGY + ALLERGEN_TAG`만 알러지로 허용, 신규 `AVOID + ALLERGEN_TAG` 차단 |
| iOS 설정 | 한 알러젠 화면에서 `ALLERGY/AVOID` 선택 | 알러지·기피 화면 분리, 알러젠 태그는 알러지 전용 |
| 판정 모드 | `strictAllergyMode`가 legacy 태그 조건을 추가 | 알러지가 있으면 항상 verified-only, 토글 없음 |
| 근거 | 식품·태그당 한 행, 실제 포함/교차접촉 미구분 | 출처별 근거 보존, `CONTAINS/MAY_CONTAIN` 구분 |
| 완결성 | 태그 행 플래그와 별도 프로필이 공존 | 검토 태그 집합·표준 버전을 가진 별도 프로필만 기준 |
| 무태그 프로필 | 브랜드 CSV가 검증 완료 무태그 행 거절 | 포함·교차접촉 0개인 완결 검토도 허용 |
| 레시피 | confidence만 구분 | 양성 포함 근거로만 차단, 통과 근거 금지 |
| 충돌 | 다중 출처 근거와 충돌 표현 불가 | 충돌 시 차단하고 알러젠 재검증 하위 큐로 전달 |
| 재적재 | 영양 사실 변화 시 추천 상태만 회수 | 제품 사실 변경 시 알러젠 프로필도 무효화 |
| 기록 전환 | iOS가 일반 기록 API 호출, 전환 서비스 미연결 | 전용 멱등 전환 API에서 현재 조건 재검증 |
| 스냅샷 | confidence와 legacy Strict 값 중심 | 정책·제한 태그·프로필·근거 버전 보존 |

## 3. 도메인 계약

### 3.1 알러지 제한

- 서버는 `ALLERGY + ALLERGEN_TAG`만 수용한다.
- `ALLERGY + FOOD/CATEGORY/KEYWORD`와 신규 `AVOID + ALLERGEN_TAG`는 API 검증과 DB `CHECK`로 거절한다.
- 활성 알러젠 태그는 정책 버전, 데이터 커버리지, benchmark 결과를 가진다.
- 활성화되지 않은 태그는 UI에 노출하지 않고 서버 등록도 거절한다.
- 이미 등록된 태그가 비활성화되면 제한을 삭제하거나 무시하지 않고 `ALLERGEN_POLICY_TEMPORARILY_UNAVAILABLE`을 반환한다.
- 자유 입력 알러지와 심각도는 수집하지 않는다.

### 3.2 알러젠 근거

권장 신규 모델은 출처별 원본 사실을 보존하는 `food_allergen_evidence` 성격의 테이블이다.

| 필드 | 의미 |
|---|---|
| `food_catalog_id` | 근거가 가리키는 식품 |
| `allergen_tag` | 표준 알러젠 태그 |
| `relationship` | `CONTAINS` / `MAY_CONTAIN` |
| `confidence_level` | `DIRECT_VERIFIED` / `LABEL_DERIVED` / `RECIPE_DERIVED` / `UNKNOWN` |
| `source` | `MFDS_CLASS` / `FOODQR` / `BRAND_OFFICIAL` 등 |
| `source_reference` | 라벨·공식 문서·데이터 원문 참조 |
| `evidence_version` | 제품·라벨·정책 버전 |
| `reviewed_at`, `valid_until` | 검토 시점과 유효기간 |
| `status` | `ACTIVE` / `SUPERSEDED` / `INVALIDATED` |

같은 식품·태그라도 출처와 버전이 다르면 별도 근거로 보존한다. 더 최신의 동일 제품 공식 전체 라벨만 이전 같은 계열 근거를 `SUPERSEDED`로 전환할 수 있다. 교차 출처 충돌은 자동 우선순위로 해소하지 않는다.

### 3.3 완결 알러젠 프로필

`food_allergen_profiles`는 포함 태그와 독립된 검토 계약이다.

- 포함·교차접촉 태그가 0개인 완결 검토도 표현한다.
- `covered_allergen_tags` 또는 정규화된 profile-coverage 관계로 검토 범위를 저장한다.
- `standard_version`, source, source reference, reviewed/valid/invalidated 상태를 보존한다.
- 사용자의 모든 제한 태그가 유효 프로필의 검토 범위에 포함돼야 한다.
- `DIRECT_VERIFIED`, `LABEL_DERIVED`만 통과 근거가 된다.
- `RECIPE_DERIVED`는 `CONTAINS`를 추가해 차단할 수 있지만 부재를 증명하지 않는다.

### 3.4 판정 순서

알러지 제한이 없으면 프로필 존재를 요구하지 않는다. 제한이 있으면 식품별로 다음 순서를 적용한다.

1. 제한 태그가 현재 정책에서 활성 상태인지 확인한다.
2. 제한 태그와 일치하는 유효 `CONTAINS/MAY_CONTAIN` 근거가 있으면 차단한다.
3. 유효 근거끼리 충돌하면 차단한다.
4. 유효 완결 프로필이 없으면 차단한다.
5. 모든 제한 태그가 프로필 검토 범위에 포함되지 않으면 차단한다.
6. 프로필 신뢰 수준·검토일·유효기간·무효화 상태를 확인한다.
7. 모두 통과하면 추천 후보로 전달한다.

`strictAllergyMode` 값은 위 순서에 영향을 주지 않는다.

## 4. 적재와 무효화

`AllergenEvidenceIngestService` 성격의 단일 경계를 두고 다음을 한 트랜잭션으로 처리한다.

1. 식품·제품 식별과 source envelope 검증
2. 출처별 포함·교차접촉 근거 저장
3. 완결 프로필과 검토 범위 저장
4. 조건을 만족하는 이전 동일 제품 근거 대체
5. 충돌 감지와 프로필 무효화
6. 추천 자격 회수와 재검증 작업 생성·노출

제품 영양·제공량·데이터 버전이 유의미하게 바뀌고 새 완결 알러젠 자료가 없으면 기존 프로필을 무효화한다. 브랜드·라벨 프로필은 최대 1년을 기본 만료 정책으로 두고, 단일 원재료 직접 검증은 정책 버전 유효성을 기준으로 장기 유지할 수 있다.

Seed SQL, 브랜드 CSV, 관리자 단건·벌크 작업은 장기적으로 이 경계를 사용한다. 신규 브랜드 메뉴는 태그만 저장하지 않고 별도 프로필까지 함께 생성해야 한다.

## 5. 관리자 재검증 작업함

관리자 화면은 하나로 유지하되 내부 조회·처리 흐름을 분리한다.

- 영양·제공량 사실 변경
- 데이터 신선도 만료
- 알러젠 프로필 만료
- 알러젠 프로필 무효화
- 알러젠 근거 충돌

초기에는 source-of-truth 상태를 사유별 DB query와 cursor pagination으로 조회한다. 담당자·처리 상태·SLA·이력이 필요해지면 `review_tasks` 테이블로 승격한다. 현재처럼 전체 후보를 메모리로 읽고 마지막에 limit하는 방식은 확장하지 않는다.

운영자는 충돌 근거를 수동 해소할 수 있지만 원본을 삭제하지 않는다. 채택·대체한 근거, 처리 사유, 토큰 식별자, 처리 시각, 정책 버전을 감사 이력으로 남긴다.

## 6. 후보 진단과 실패 계약

추천 파이프라인은 다음 단계별 수치를 수집한다.

1. 기본 추천 가능 후보
2. 현행 기피 조건 통과 후보
3. 알러젠 안전 게이트 통과 후보
4. 데이터 최신성 통과 후보
5. 영양 완전성 통과 후보
6. 제공량 검증 통과 후보
7. 최적화 가능 후보

실패 코드는 최소한 다음을 구분한다.

- `ALLERGEN_VERIFIED_POOL_INSUFFICIENT`
- `ALLERGEN_POLICY_TEMPORARILY_UNAVAILABLE`
- `AVOIDANCE_FILTER_POOL_INSUFFICIENT`
- `NUTRIENT_DATA_INCOMPLETE`
- `SERVING_OPTIONS_INFEASIBLE`
- `NUTRITION_CONSTRAINT_INFEASIBLE`

단계별 수치는 설명과 검증 우선순위에만 사용하며 조건을 자동 완화하지 않는다. 자유 기피 키워드 원문은 장기 스냅샷·분석 이벤트·운영 로그에 저장하지 않는다.

## 7. API와 iOS

### 7.1 제한 설정

- 알러지와 기피 설정을 별도 화면으로 분리한다.
- 알러지 화면은 활성 `ALLERGEN_TAG`만 선택할 수 있고 type picker를 두지 않는다.
- 기피 화면에서는 알러젠 태그 선택을 제거한다. 나머지 현행 기피 기능은 이번 범위에서 변경하지 않는다.
- 현재 운영 데이터에 `AVOID + ALLERGEN_TAG`가 없으므로 데이터 변환 없이 신규 조합만 차단한다.

### 7.2 추천 요청·응답

- iOS에서 Strict 토글을 제거한다.
- 서버는 호환 기간 동안 `strictAllergyMode`를 받되 무시한다.
- 응답과 스냅샷은 `allergyPolicyVersion`을 제공한다.
- 추천 식품은 알러젠 프로필 source, reviewedAt, 필요 시 validUntil을 제공한다.
- 안내 문구는 "검증된 정보 기준이며 실제 제품·제조 환경은 달라질 수 있으니 섭취 전 라벨을 확인해 달라"는 범위를 유지한다.

### 7.3 추천 기록 전환

일반 식단 기록 API는 유지한다. 추천 끼니는 전용 전환 API를 사용한다.

1. 스냅샷 소유권과 `snapshotId + mealType` 멱등 키 확인
2. 현재 알러지·기피 제한 재조회
3. 식품 상태, 알러젠 근거·프로필 재검증
4. 통과 시 식단 기록 생성
5. 같은 트랜잭션에서 전환 이벤트 저장

이미 전환된 끼니의 동일 재시도는 기존 결과를 반환한다. 사용자가 직접 기록하는 일반 API는 알러지 조건 때문에 차단하지 않는다.

## 8. 스냅샷과 보관

추천 스냅샷에는 다음 최소 재현 정보를 저장한다.

- `allergyPolicyVersion`
- 추천 당시 제한 알러젠 태그 집합
- 식품별 알러젠 프로필 식별자·버전
- 판정에 사용한 근거 버전·검토일
- 최종 알러젠 판정

사용자 연결 스냅샷은 90일 보관한다. 이후 사용자 식별 정보와 제한 태그를 제거하고 정책 버전, 성공·실패 코드, 단계별 후보 수 같은 비식별 집계만 유지한다.

## 9. 테스트와 단계 출시

### 9.1 TDD 순서

1. 제한 조합 불변 조건과 DB 제약
2. 알러젠 근거 관계·상태와 프로필 검토 범위
3. fail-closed `AllergenSafetyGate`
4. 근거 적재·대체·충돌·무효화
5. 후보 단계별 진단과 실패 분류
6. 추천 스냅샷 근거 버전
7. 추천→기록 멱등 전환과 재검증
8. iOS 분리 화면·Strict 제거·근거 표시

### 9.2 필수 시나리오

- 제한 `CONTAINS` 또는 `MAY_CONTAIN` 근거가 있으면 차단
- 유효 프로필이 없거나 제한 태그를 검토하지 않았으면 차단
- 포함 태그 0개 + 완결 프로필이면 통과
- `RECIPE_DERIVED` 양성 근거는 차단, 음성은 통과 근거가 아님
- 프로필 만료·무효화·근거 충돌은 차단
- 알러지 미등록 사용자는 프로필 없이 통과 가능
- 비활성 정책 태그는 조건을 무시하지 않고 구조화된 실패
- 일반 기록은 유지되고 추천 전환만 현재 조건 재검증

### 9.3 benchmark와 롤아웃

1. 새 스키마와 적재 경계 배포
2. Seed·브랜드 legacy 태그와 프로필 백필
3. 무결성 검사와 고정 benchmark
4. 새 게이트 shadow 판정으로 기존 결과 비교
5. 우유·달걀·밀·땅콩 등 최소 세트부터 태그별 활성화
6. 알러지·기피 분리 UI 공개

단일 알러젠, 주요 복합 알러젠, 목표 유형, 3끼·4끼를 조합한다. 알러젠 위반은 0건이어야 하며 불가능한 조건은 성공 추천이 아니라 정확한 실패를 반환해야 한다.

## 10. 성능 전환 기준

현재 추천 후보 규모에서는 Java `AllergenSafetyGate`를 최종 판정으로 유지한다. 후보 수, 태그 수, 프로필 수, 게이트 처리 시간과 API p95를 측정한다.

검증 풀이 수천 건으로 늘거나 p95 기준을 초과하면 다음 DB 선필터를 추가한다.

- 유효 완결 프로필 `EXISTS`
- 제한 태그의 유효 `CONTAINS/MAY_CONTAIN` 근거 `NOT EXISTS`

DB 선필터는 성능 최적화일 뿐이며 Java 게이트를 제거하지 않는다.

## 11. 완료 기준

- 기본/Strict 2모드가 제거되고 알러지 등록 사용자는 항상 verified-only다.
- 잘못된 제한 조합이 UI·API·DB에서 생성되지 않는다.
- 여러 출처의 포함·교차접촉 근거, 버전, 대체·무효화 이력을 보존한다.
- 무태그 완결 프로필과 검토 태그 범위를 표현한다.
- 제품 변경·만료·충돌이 추천을 fail-closed로 회수한다.
- 알러젠 하위 재검증 큐와 감사 가능한 수동 해소가 가능하다.
- 단계별 후보 진단과 구조화된 실패가 실제 원인을 구분한다.
- 추천 스냅샷과 전환이 정책·근거 버전을 재현하고 현재 조건을 재검증한다.
- 활성 태그별 benchmark에서 알러젠 위반이 0건이다.
