## 0. ⚠️ 기존 포지셔닝 문서와의 긴장 관계 (반드시 먼저 읽을 것)

이전 세션이 남긴 `GAINSY_POSITIONING_STRATEGY_2026-07.md`는 다음 결론을 담는다:

> **포지션:** "한 주의 기록을 변화의 증거와 다음 행동으로 바꾸는 한국형 주간 변화 코치"
> **타깃:** 주 2~5회 운동하며 감량·근증·체형개선을 시도하는 한국 iPhone 사용자(넓음)

이번 두 차례 회의는 여기서 **한 단계 더 좁혔다**:

> **포지션:** "한국 음식으로 목표 매크로를 맞춰야 하는 사람을 위한 식단 설계 도구"
> **1차 beachhead:** GLP-1(위고비/마운자로) 복용 중 근손실 방지 세그먼트(좁음)

**두 문서는 모순이 아니라 줌 레벨의 차이다.** 기존 문서 = 브랜드 상위 서사(주간 변화 루프), 이번 문서 = 그 서사로 **처음 확보할 좁은 진입 시장(beachhead)**. beachhead에서 이기면 기존 문서의 넓은 타깃으로 확장한다. 단 **온보딩·ASO·스토어 카피는 beachhead(GLP-1)에 먼저 정렬**하고, 앱 전체 서사는 "주간 변화 루프"를 유지한다.

> 결정 필요(사용자): 두 문서를 통합할지, 상/하위 관계로 병존시킬지. 현재는 **병존 + 상호 링크**로 둔다.

## 1. 라운드테이블 1차 — 시장·포지셔닝·브랜드·UX

### 1.1 PEST (Gainsy에 실제로 꽂히는 것만)
- **[위협·최대] 사진→칼로리는 끝난 시장.** Cal AI 18개월 ARR $50M 후 MyFitnessPal에 인수(2026.3). **우리 AI 사진분석은 차별점이 아니라 입장료.**
- **[기회·최대] GLP-1.** 국내 위고비·마운자로 누적 처방 200만건 돌파. 문제는 "칼로리 줄이기"가 아니라 **줄어든 총량 안에서 단백질 채우기** = 우리 제약최적화 엔진이 푸는 문제.
- **[기회] 온디바이스 LLM(Apple Foundation Models).** iOS 전용이라는 약점이 여기서만 강점으로 뒤집힘.
- **[정치] 비의료 건강관리 가이드라인.** "차분한 헬스 코치" 보이스가 이미 규제 정합. `BEHIND` 문구가 "위험" 뉘앙스로 가면 회색지대.

### 1.2 Porter's Five Forces
| Force | 강도 | 한 줄 |
|---|---|---|
| 신규 진입장벽 | 하 | 공공DB 무료 + Vision API = 3개월 복제 가능 |
| 대체재 | 상 | OS 번들 무료 + GLP-1 약물 + PT |
| 구매자 교섭력 | 상 | 전환비용 0. 락인은 누적 사진·추세·30일 swap 프로필 |
| 공급자 교섭력 | 중 | 공공DB 하 / OpenAI 중 / Apple 상 |
| 기존 경쟁강도 | 상 | 정면충돌 회피 필수 |

**함의:** 트래커 시장(=무엇을 먹었나)은 레드오션. **"오늘 뭘 먹지"(=무엇을 먹을까)를 제약조건까지 지켜 답하는 한국어 앱은 사실상 없다**(Eat This Much 하나, 한국화 안 됨).

### 1.3 SWOT 핵심
- **S:** 기록→추천→회고 폐루프 · 결정적·설명가능 추천(LLM 아님) · 공공DB 62만행 한식 커버리지 · 동일식품 1일 1회 hard 제약 · swap 사유 자산화 · 접근성/i18n 완성도
- **W:** 알러젠 검증 풀 병목(direct 24) · 안드로이드 부재 · **유저획득 채널 0** · AdMob 단독 수익 · HealthKit 미연동 · 버스팩터 1
- **O:** 한식 자동 식단설계 = 빈 칸 · MFP 구독 압박 이탈 · 접근성으로 App Store 피처링 · GLP-1 세그먼트
- **T:** MFP/Yazio가 매크로 식단생성 붙이면 한 분기에 소멸 · **알러지 오판 1건 = 신뢰 붕괴 + 법적 리스크** · 공공DB 스키마 변경 · 광고 단독으론 재투자 불가

### 1.4 채택 포지셔닝 [확정]
> **"Gainsy는 한국 음식으로 목표 매크로를 맞춰야 하는 사람을 위한 식단 설계 도구다. 국내 공공 식품DB 62만행 위에서 제약최적화로 하루 끼니를 짜기 때문이다."**

핵심가치 3층: (기능) 못 먹는 걸 빼고 실제 단위로 끼니를 정해줌 + 주 단위 방향 판정 / (정서) 식단 결정 피로 해방, 죄책감 아닌 **차분한 확인** / (자기표현) 유행 다이어트가 아니라 **근거로 관리하는 사람**.

### 1.5 해자 진단 [확정]
| 층위 | 판정 |
|---|---|
| 제약최적화 엔진 | 복제 가능(한 분기). **여기에 해자 없음** |
| 한식 DB 정합화 + 실제 제공량 매핑 | 해외 앱은 ROI 안 나와 안 함. 국내 경쟁사는 가능 |
| swap 사유 누적 데이터 | 복제 불가에 가까움. **단 사용자 없으면 존재 안 함 → 현재는 "해자 후보"** |

**결론: 지금 moat는 약하다. 기술이 아니라 데이터·유통이 해자여야 한다.** 보강 순서 = ① 알러젠 풀 확장 → ② swap→개인화 체감 성능 증명 → ③ 한식 DB 깊이.

### 1.6 브랜드 아이덴티티 [가설]
- 퍼스널리티 = 능력(Competence) 주축 + 성실 보조. 의인화 = **33세 임상영양사 출신 트레이너, 데이터를 먼저 펼치고 결론은 사용자에게 넘김.** "차분한 헬스 코치"의 날카로운 정의 = **"근거를 먼저 보여주고 결론은 미루는 사람"**.
- 네이밍: 'Gainsy' 감량 사용자 인지부조화 실재하나 **리브랜딩 비권장**. Gain을 '얻는 것(근육·기록·습관)'으로 재프레이밍. 회고 헤드라인 고정 포맷 "이번 주 얻은 것 — 기록 5일, 단백질 +12g/일".
  - 리브랜딩 트리거(2개↑): 감량목표 가입 60%↑ / 목표선택 이탈 25%↑ / "벌크업 앱인 줄" 리뷰 월 3건↑
- 시각: Forest 톤 **유지 후 진화**(파랑=MFP, 노랑=Noom, 핑크=국내 → 초록은 빈 축). 숫자/본문 위계를 크기 아닌 **종류**로 가름. 그림자 대신 배경 명도차 = "놓여 있는 인상".
- 금지 6종: 전후 비교 / "D-30·−3kg" 압박 / 파스텔 그라디언트 / 이모지 / 바벨·근육 실루엣 / 컨페티.

## 2. 라운드테이블 2차 — 수익·추천·타깃

### 2.1 수익모델 [확정: 방향 동의]
**관통 원리:** 가장 차별화된 기능(식단추천)이 **원가 0**(순수 Java, LLM 없음), 원가 나가는 기능(AI 사진)이 차별화 약함 → **싼 자산을 유료 훅, 비싼 기능을 무료 미끼+횟수제한.**

- 모델: 소액 구독(freemium) 축 + Lifetime 얼리버드 병행.
- Freemium 경계: 홈 추천 무료 1끼/유료 3끼, swap 무료 월3회/유료 무제한, **알러지 안전게이트는 항상 무료**, AI 사진 무료 월5회(미끼)/유료 월30회.
- Paywall 위치: **대안 swap 4회째 + 주간회고 열람**(첫 추천 직후 아님).
- 가격: 월 ₩3,900(앵커) / **연 ₩24,900(기본)** / Lifetime ₩49,000(100명 한정). 손익분기 = 연 ₩24,900 기준 57명(가격 3~4만원대면 35명).
- **⚠️ 유료화 점등 기준: MAU 500 + D7 리텐션 20% 도달 시.** 그 전엔 Phase 0(무료·계측).
- 금지 3종: 광고+구독 동시 공격 / 조기 유료화 / GLP-1·의료 소구 유료화.

### 2.2 식단 추천 영양학 판정 [확정]
> **"방향은 맞으나 영양 충실성(미량영양·지방하한·개인화)이 빠졌다."** 근본 재설계 불필요, 뼈대(안전·결정성·투명성) 견고.

코드 근거 구멍:
- `NutritionCalculator.java:61-70` — 목표 조정이 체중 무관 **일괄 -500/+300 kcal** (50kg 여성 TDEE 30% 결손 = 근손실 위험).
- `GoalAwareNutritionPolicy.java:19-45` — 감량 시 **지방 하한 0(`unconstrained()`)** = 가장 명백한 영양 구멍.
- §5.1 비대칭 밴드는 아직 엔진에 없음(문서 가설).

다음 분기 최우선 3가지: ① 지방 하한 + 섬유 soft 목표(코드 최소·임팩트 최대) ② ⓪ 검증풀 54→90+(모든 강화의 선결) ③ 목표 칼로리 개인화 + swap 사유 환류.

브랜드 카피 원칙: 팔 것은 "정확함"이 아니라 **"정직한 안전"**. "AI가 짜준 완벽한 식단"은 규제 위반+실제로 거짓(미량영양 미반영). 대신 *"등록한 알러지·기피를 단 한 번도 어기지 않는 추천"*.

### 2.3 타깃 확정 [확정]
1차 beachhead = **② GLP-1 복용 중 근손실 방지.** 근거 = "발견가능성 × 지불의사 × 무방비 경쟁" 세 조건의 곱을 유일하게 충족(급성장 신규수요 + 약값 내는 고지불층 + 전용 도구 부재 + "위고비 근손실" ASO 무주공산). 2차 = ① 알러지(안전게이트 재사용).

페르소나: **민준(34, 위고비 3개월차, 8kg 빠졌지만 거울은 축 처짐).** JTBD = "식욕 없는 상태에서도 근육 지킬 단백질을 한국 음식으로 챙기고 싶다." 총칼로리 강조는 무의미(이미 적게 먹음), **남은 단백질 예산**이 전부.

기능 포트폴리오(2차 라운드 원안 — §3 팩트체크로 일부 수정됨):
- CORE: 식단추천 · 매크로 예산 엔진 · 알러지 게이트
- SUPPORT: 식단기록 · 신체측정 · 주간회고("단백질 달성"으로 재편)
- QUESTION: 홈위젯 · 운동기록(유지보수만)
- KILL/FREEZE(원안): 진행사진 · Explore 탭 → **§3에서 재판정**

North Star: 주간 "단백질 목표 달성일 ≥4일" 활성유저 수. Pivot: 3개월 내 GLP-1 프리셋 선택 <15% 또는 추천→기록 전환 <10%면 ②→① 전환.

## 3. 팩트체크 — 진행사진 · Explore 탭 (코드 실측)

### 3.1 Explore 탭 → **제거 확정** [확정, 사용자 인정]
- ViewModel **9줄**, `load()`는 완전 빈 함수. View 128줄. 자체 콘텐츠 **0** — 주간회고·변화분석으로 가는 **네비게이션 우회로**일 뿐(`ExploreView.swift`).
- 탭바 5개 중 하나(`safari` 아이콘). 하단 광고배너 1개(`ExploreView.swift:28`).
- **결정:** 회고·변화분석을 홈에서 직접 진입하게 하고 탭 제거(4→3탭). 배너는 홈 하단으로 이전 → **수익 손실 없음**.
- 실행 전 확인: AdMob 대시보드에서 Explore 배너 수익 비중(참고용).

### 3.2 진행사진 → **죽이지 않음, 활용성 강화로 전환** [확정, 사용자 결정]
팩트:
- 코드 ~2,200줄(백엔드 816 + iOS 1,352 + 마이그레이션 2). S3 presigned + EXIF 제거 + 썸네일(이미지 프로세서 126줄).
- 사용률 계측 **0**(백엔드 Micrometer 0건, iOS 이벤트 로깅 0건. Firebase는 FCM 전용).
- **사용자 확인: 실제 활용 ~0건, S3 비용 청구 0원.**

사용자 판단(채택): **"사진으로 자신의 실제 몸을 확인하는 기능은 필요하다."** 근손실은 체중계가 아니라 **거울(=진행사진)**로 드러나므로 GLP-1 beachhead와 오히려 정합. 서브에이전트의 KILL 판정 **반려**.
→ 새 과제: **진행사진 활용성 강화 방안**(§4에서 탐구).

### 5.1 진행사진 활용성 강화 [탐구 완료 2026-07-24]

**전제(코드 실측):** 기능은 이미 풍부하다 — 5포즈(`FRONT/BACK/SIDE_LEFT/SIDE_RIGHT/DETAIL`), baseline 지정, 2장 나란히 비교(`PhotoCompareView`), 사진별 체중/체지방/허리 메타(`ProgressPhotoModels.swift:bodyWeightKg/bodyFatPct/waistCm`), 썸네일 3종, EXIF 제거. **결핍은 기능이 아니라 (a)발견 불가 (b)GLP-1 서사 미연결 (c)촬영 습관 부재 (d)민감정보 안심 메시지 부재.**

**왜 지금 안 쓰이나 (진단):**
- 진입점이 Record→BodyMeasurement 3뎁스 안. 홈 노출 0. (`ProgressPhotoView.swift`는 상위 네비에서만 도달)
- "언제 찍어야 하는지" 신호가 없음 — 사진은 데일리가 아니라 **2주~월 단위 의식(ritual)**인데 트리거가 전무.
- 숫자(체중)와 분리돼 있음 — 근손실 서사("체중은 줄고 거울은 처짐")를 만들 수 있는데 사진과 지표가 같은 화면에 안 붙음.
- 몸 사진 = 민감정보. 저장 자체를 꺼리는 심리 장벽에 대한 안심 카피가 없음.

**활용성 강화안 (impact/effort):**

|---|---|---|---|---|

### 5.2 데일리·위클리·먼슬리 리텐션 루프 [탐구 완료 2026-07-24]

**핵심 통찰:** 리텐션은 **"결과가 눈에 보이는 시간축"이 지표마다 다르다**는 사실을 설계에 반영해야 성립한다. 하나의 피드백만 주면 실패한다 — 데일리만 주면 피로, 장기만 주면 오늘 열 이유가 없음. **세 리듬 각각에 고유한 페이오프(payoff) 순간**을 배치한다.

| 리듬 | 지표(가시화 시간축) | JTBD | 페이오프 순간 | 현재 상태 |
|---|---|---|---|---|
| **데일리** | 칼로리·단백질(당일 가시) | "오늘 부족한 단백질을 뭘로 채우지" | 홈에서 "지금 단백질 28g 부족 → 두부조림" **능동 처방** | 링은 있으나 수동 요약(`ActivityRingPanel`). **처방 없음** |
| **위클리** | 체중·연속일(주 단위 추세) | "이번 주 방향이 맞나" | 월요일 회고 = ON_TRACK 판정 + **다음 주 한 가지** | 회고 존재하나 Explore에 묻힘(제거 예정). Monday FCM 있음 |
| **먼슬리** | 근육·체형·사진(월 단위 가시) | "정말 효과가 있나 (증거)" | **"이번 달 얻은 것" 리포트** = 체중추세 + 근육유지 + 사진 before/after + 단백질 달성률 | **없음.** 최대 공백 |

**설계 처방:**
1. **데일리를 요약→처방으로 전환.** 홈 히어로(§1.7 F2 처방)가 "이미 한 일"이 아니라 "지금 할 일"을 말하게. GLP-1 페르소나에겐 총칼로리 대신 **남은 단백질 예산**이 데일리 훅.
2. **위클리를 홈으로 끌어올림.** Explore 제거로 비는 슬롯에 회고를 홈 하단 섹션으로 편입(D4와 연동). 월요일 FCM은 유지하되 "판정 + 다음 한 가지 CTA"로 강화.
3. **먼슬리 리포트 신설 = 리텐션의 진짜 엔진.** 몸의 변화는 월 단위로 보인다. "이번 달 얻은 것" 리포트가 **"아, 되고 있구나" 순간**을 만들고 장기 리텐션·입소문을 만든다. 여기에 진행사진 before/after(§5.1 P1)를 넣으면 사진 기능의 존재 이유가 완성됨. 매월 1일 FCM.
   - 카피(브랜드 보이스): "이번 달 얻은 것 — 체중 -2.4kg, 골격근 유지, 기록 22일, 단백질 목표 18일 달성."
4. **먼슬리 페이오프에 진행사진을 묶는다.** §5.1 P4(격주 촬영 프롬프트)의 결과물이 월간 리포트의 before/after로 회수됨 → 사진 촬영 동기와 리텐션이 한 루프로 닫힘.

**리텐션 루프 통합도:**
```
[데일리] 홈: 남은 단백질 처방 → 추천 → 기록
   ↓ (누적)
[위클리] 월요일 회고: 판정 + 다음 주 한 가지 + 격주 진행사진 촬영
   ↓ (누적)
[먼슬리] 매월 1일 "이번 달 얻은 것": 체중·근육·사진·단백질 → "되고 있다" 증거
   ↓
   재동기 → 데일리로 복귀
```

**우선순위:** 데일리 처방(§1.7 F2·홈 히어로)과 위클리 회고 이전(D4)은 이미 실행 큐에 있음. **신규 최우선 = 먼슬리 "이번 달 얻은 것" 리포트** — 현재 가장 큰 리텐션 공백이자, 진행사진·근손실 서사·brand("이번 주/달 얻은 것" 포맷)를 한 번에 회수하는 지점. 공수 M~L, 임팩트 상.

> 다음 액션 후보(사용자 결정 대기): (a) 먼슬리 리포트를 이슈로 끊기 (b) 진행사진 P3+P1 먼저 (c) Explore 제거 + 회고 홈 이전부터.

**실행:** (a) 채택 → **이슈 #92 생성**(2026-07-24) — "feat: 월간 '이번 달 얻은 것' 리포트 — 먼슬리 리텐션 페이오프 신설"(label: enhancement). https://github.com/KimGiii/Gainsy/issues/92

### 8.6 #109 다중 간식 백엔드 대응 [2026-07-30 신설]

#105로 iOS가 `mealTypes`에 `SNACK`을 최대 3개 중복 전송하게 됐다. 백엔드를 실측 검토한 결과 **칼로리 배분은 정상**이나 3건이 미대응이다. 이슈 #109.

#### 정상 확인 (수정 불필요)

| 항목 | 근거 |
|---|---|
| 칼로리 배분 | `totalRatio`가 중복을 합산(0.25+0.10+0.35+0.10+0.30+0.10=1.20) → 각 간식 8.3%, 합 100% |
| 끼니 생성 | `for (MealType mealType : selectedMeals)`가 List 순회 → 중복이 별도 끼니 생성, 응답 순서도 요청 순서 보존 |
| 단백질 하한 휴리스틱 | `canReachProteinFloorWithinSelectedMealSlots`가 per-entry 합산 |
| 스냅샷 저장 | 전체 리스트 직렬화, `mealType` 키잉 없음 → 충돌 없음 |

#### 대응 필요

| # | 문제 | 심각도 | 내용 |
|---|---|---|---|
| **B1** | 간식 슬롯이 주식·단백질로 채워짐 | **HIGH** | `PREFERRED_CATEGORIES[SNACK]`은 9개 중 3개(과일·유제품·가공)뿐. `usedFoodIds`가 하루 전체 누적 hard 제외라 아침이 유제품·과일을 먼저 소진하면, `fillRemaining(newCategoryOnly=false)`의 카테고리 무관 보충이 2·3번째 간식을 쌀밥·닭가슴살로 채운다. **성공 응답 내부의 품질 저하라 실패율 지표에 안 잡힌다** |

| **B3** | 슬롯 수 관측 불가 | MEDIUM | 실패 카운터가 `reason`만 태깅. **"간식 3개 요청이 더 실패하나"를 답할 수단이 없는 상태로 출시됨** |

#### 착수 순서

B2·B3(저위험·즉시 관측 확보) → B1(품질, 벤치마크로 발생률 정량화 후 설계).

1. **B2 검증 추가** — 메인 끼니 중복 거부, 간식 최대 3개, 전체 슬롯 상한
2. **B3 계측 추가** — 실패·성공 카운터에 슬롯 수·간식 수 태그. B1 발생률의 관측 기반이 된다
3. **B1 정량화** — `RecommendationFeasibilitySweep`에 간식 1/2/3개 시나리오 추가, 간식 슬롯의 비적합 카테고리 혼입률 측정
4. **B1 수정** — 간식 fallback에서 주식·단백질원 배제 또는 간식 전용 보충 순서. 적합 후보 고갈 시 무리하게 채우지 않고 슬롯 축소·실패 설명
5. **중복 SNACK 테스트** — 현재 커버리지 0건(`grep` 확인)

> **ⓠ 검증풀 확장과의 관계**: B1의 근본 원인은 간식 적합 후보의 절대 부족이다. 코드 수정은 "부적합 식품을 넣지 않는다"까지만 가능하고, "적합 식품을 넣는다"는 검증풀 확장(과일·유제품·간식 대체군 우선)이 있어야 성립한다. §8.2 상시 트랙의 우선순위 근거가 하나 더 늘었다.
