후보 1 · 반복 기피 정렬은 죽어 있다

테스트 통과 + 운영 효과 0 — 이 스킬이 정확히 겨냥하는 안티패턴

파일

  • UserRepetitionPolicy.java (Unit 5)
  • DailyDietRecommendationUseCases.java:95–105
  • DietRecommendationEngine.java:74, 221–234

문제

UseCase가 repetitionPolicy.sortByPreference(candidates)로 최근 먹은 음식을 뒤로 보낸 뒤 engine.recommend(preferredCandidates)를 호출한다. 그런데 엔진은 끼니마다 sortByScore()로 후보를 처음부터 다시 정렬한다. 이 비교자는 rotationKey(date)가 사실상 순서를 결정하며 반복 페널티를 전혀 보지 않는다. 입력 순서는 마지막 동점 처리(unique stableKey 이후)라 절대 도달하지 않는다.

deletion test

sortByPreference 호출을 지우고 candidates.foods()를 그대로 엔진에 넘겨도 출력은 한 글자도 바뀌지 않는다. → 현재 이 모듈은 레버리지 0의 pass-through. 버그는 함수 안이 아니라 호출 방식에 있다.

before — 두 개의 정렬 seam, 뒤가 앞을 덮어씀

candidates.foods()
▼
sortByPreference() · 반복 페널티
▼ preferredCandidates
engine.sortByScore() · rotationKey
↑ 처음부터 재정렬, 앞 순서 폐기
▼
반복 기피 반영된 추천

after — 점수화 seam 하나로 융합

candidates.foods()
▼ + RepetitionPolicy 주입
engine.sortByScore(policy)
penalty → rotationKey → usage → stableKey
하나의 비교자에 반복 페널티 포함
▼
반복 기피가 실제로 반영된 추천

해법 (영문 설명 아님 — 평이하게)

점수화 seam을 엔진 한 곳으로 합친다. sortByScore가 UserRepetitionPolicy(또는 penalty 함수)를 받아 비교자 맨 앞 키로 쓰게 한다. UseCase는 정책을 만들어 주입만 하고 직접 정렬하지 않는다. 그러면 반복 페널티가 끼니별 재정렬에서도 살아남는다.

이득 (locality · leverage · 테스트)

  • Leverage: "최근 먹은 건 덜 추천한다"가 모든 끼니·대안에 일괄 적용된다.
  • Locality: 추천 순위 규칙이 sortByScore 한 곳에 모인다. 지금은 UseCase와 엔진에 흩어져 충돌.
  • 테스트: "어제 먹은 닭가슴살이 오늘 추천 뒤로 간다"를 엔진 출력으로 검증 — 현재 단위 테스트는 호출되지 않는 함수를 검증 중.
Strong

후보 2 · 엔진이 검증된 제공량 옵션을 무시한다

⚠ ADR-0002 §5와 직접 충돌 — "추천 엔진은 임의 g 대신 검증된 이산 제공량 옵션을 사용한다"가 미구현 상태.

문제

DietRecommendationCandidate는 이제 servingOptions와 hasVerifiedServingOptions를 싣고 다닌다(후보 풀이 4번째 병렬 쿼리로 적재, iOS 프리셋도 연결됨). 그러나 엔진의 calculateServing()은 이 필드를 한 번도 읽지 않고 targetCalories / kcal100 × 100을 25g 단위로 반올림할 뿐이다. 후보 풀과 iOS가 들인 제공량 작업이 추천 알고리즘에 0% 반영된다.

deletion test

DietRecommendationCandidate에서 servingOptions 두 필드를 지워도 추천 엔진은 컴파일·동작 모두 영향 없음. 소비처는 응답 직렬화/iOS 뿐 — 추천 깊이에는 기여 0.

before

double rawServing =
    targetCal / kcalPer100g * 100;
double rounded =
    round(rawServing / 25) * 25;  // 임의 g
return clamp(25, 500, rounded);
// servingOptions 무시됨 ✗

"닭가슴살 137g" 같은 비현실적 제공량 발생 가능

after — ServingSelector seam

servingSelector.choose(
    food.servingOptions(),
    targetCalories)
// 검증된 옵션 우선,
// 없으면 25g step fallback
// → "1쪽(100g)", "1컵(240g)"

검증 옵션 → 이산 프리셋, 미검증 → 기존 fallback

해법

제공량 결정을 작은 깊은 모듈 ServingSelector(또는 후보의 chooseServing(targetCalories) 메서드)로 만든다. 검증된 옵션이 있으면 가장 가까운 이산 옵션을, 없으면 현재의 25g 스텝을 쓴다. 엔진은 "제공량은 셀렉터가 안다"만 알면 된다.

  • Leverage: 미검증 식품은 기존 동작 유지, 검증 식품은 즉시 현실적 제공량으로 업그레이드.
  • Locality: "제공량을 어떻게 정하나"가 한 곳에. 지금은 엔진 안 5줄 + 무시되는 후보 필드로 분리.
Worth exploring

후보 3 · UseCase가 얕은 82줄 오케스트레이터

작은 인터페이스(recommend(userId, request))는 좋지만, 구현이 응답 조립 디테일을 흘린다.

문제

  • 한 메서드가 8개 협력자(레포 5 + 풀 + 엔진 + 스냅샷)를 순차 호출.
  • DailyDietRecommendationResponse 11-인자 생성자가 2곳(조기 종료 82행, 정상 127행)에서 중복. 필드 추가 시 양쪽 수정 필요 — 실제로 이번 작업에서 한 번 어긋났던 지점.
  • checkTargets()가 실패 사유를 문자열로 반환, succeeded()는 null 검사 — 비즈니스 규칙이 문자열에 숨음.

현재 흐름

user → goal → targets → restrictions
→ consumed → [조기종료 응답 ①]
→ pool.load → repetitionPolicy
→ engine.recommend → checkTargets
→ recommendAlternatives → sortByDiversity
→ serializeMeals → snapshot.save
→ [정상 응답 ②]

해법 (가벼운 단계부터)

  1. 응답 생성을 DailyDietRecommendationResponse.of(...) 정적 팩토리 / 빌더로 모아 11-인자 중복 제거.
  2. 대안 생성+다양성 정렬+스냅샷 저장을 엔진/스냅샷 쪽 한 호출로 묶어 UseCase는 "조립"만.
  3. (선택) failureReason 문자열을 RecommendationOutcome 값 객체로 — UI 문구와 규칙 분리.

※ ADR-0002/0004가 정의한 "UseCase는 조립, 엔진은 끼니 구성" 경계는 유지 — 이건 그 경계를 더 선명히 하는 방향.

Worth exploring

후보 4 · 알러젠 "검증됨" 개념이 3곳에 분산

FoodAllergenTag
.allergenProfileVerified

태그 행의 boolean 플래그

FoodAllergenProfile
.isVerifiedAt(now)

신뢰도+만료+무효화 종합 메서드

AllergenSafetyGate
.hasHighConfidenceVerifiedTag

게이트 내부 로직

세 개념이 부분적으로 겹치지만 의미가 미묘히 다르다. 안전 게이트를 다른 곳(검수 큐, 관리자 리포트)에서 재사용하려면 어느 것을 믿어야 하는지 매번 추론해야 한다. ordinal() 기반 신뢰도 비교는 enum 순서 변경에 취약(현재 DIRECT_VERIFIED < LABEL_DERIVED < … 가정).

after

검증 상태를 하나의 값/메서드 AllergenVerification.evaluate(tags, profile, clock)로 모아 SafetyDecision만 노출. 호출자(풀·게이트·리포트)는 boolean 세 개가 아니라 결정 하나를 본다. 신뢰도 비교는 ordinal() 대신 명시적 순위 메서드로.

⚠ ADR-0001/0002의 안전 계약(포함 태그 의미, verified-only 게이트)은 그대로 유지 — 표현만 한 seam으로 통합.

Speculative

후보 5 · 스냅샷 감사 일관성 틈

관찰

  • Snapshot.create()가 GENERATED 이벤트를 snapshotId=null로 @Transient 리스트에 넣지만, SnapshotStore.save()는 스냅샷만 저장 → GENERATED 이벤트 유실.
  • 피드백/전환 서비스는 getEvents().getLast()를 다시 저장하는 2단계 — 두 번째 저장 실패 시 이벤트만 유실.
  • serializeMeals(meals)는 1차 식단만 저장. 응답엔 alternatives가 있지만 스냅샷엔 없음 → 나중에 "그때 뭘 대안으로 줬나" 복원 불가.

왜 Speculative인가

대안 미저장은 의도일 수 있다(대안은 요청마다 휘발). GENERATED 유실도 현재 지표 계산엔 치명적이지 않을 수 있다. 다만 ADR-0002 §6이 "노출·재추천·기록 전환 이벤트 저장"을 명시하므로, 이벤트 영속화 경로를 save() 한 트랜잭션 안으로 합칠지 결정이 필요하다.

top recommendation

먼저 후보 1 — 반복 기피 정렬 융합

이건 단순 리팩터가 아니라 조용한 정확성 버그다. Phase 4 Unit 5에서 들인 "최근 7일 반복 기피"가 운영에서 전혀 작동하지 않고, 단위 테스트는 호출되지 않는 함수를 검증해 녹색이다. 이 스킬이 가장 경계하는 패턴 — "테스트 가능성 때문에 순수 함수를 뽑았지만 진짜 버그는 그걸 부르는 방식에 숨는다" — 의 교과서적 사례다. 수정 범위도 작다: sortByScore가 정책을 받게 하고 UseCase의 사전 정렬을 제거.
