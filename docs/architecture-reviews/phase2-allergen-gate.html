#1 strictAllergyMode — 묵음으로 사라지는 파라미터 Strong 버그 수준
DietRecommendationCandidatePool.java AllergenConfidenceGate.java FoodAllergenProfileGate.java
문제

DietRecommendationCandidatePool.load(restrictions, strictAllergyMode)는 strictAllergyMode를 파라미터로 받지만, 내부 CandidateRestrictions 레코드에는 저장하지 않고 applyRuntimeGate()에도 전달하지 않는다. 결과적으로 Strict 모드가 켜져 있어도 게이트는 항상 동일하게 동작한다. AllergenConfidenceGate.passesGate()는 strictMode 파라미터를 받지만 이 메서드 자체가 아예 호출되지 않는다.

⚠ Deletion Test
strictAllergyMode 파라미터를 삭제해도 동작이 바뀌지 않는다. 이 파라미터는 현재 패스-스루(pass-through)다 — 인터페이스 계약이 구현과 분리되어 있다.

문제

"식품이 알러지 사용자에게 안전한가?"라는 하나의 질문에 대해 두 개의 게이트 (AllergenConfidenceGate, FoodAllergenProfileGate)가 서로 다른 데이터 구조를 받아 독립적으로 판단하고, CandidatePool이 두 결과를 직접 조합한다. 게이트를 추가하거나 로직을 바꾸려면 CandidatePool을 함께 수정해야 한다.

#3 applyRuntimeGate — DB 필터와 메모리 필터 중복 탐색 가치
DietRecommendationCandidatePool.java FoodCatalogSpecs.java
문제

loadCatalogCandidates()는 DB 레벨에서 FoodCatalogSpecs.idNotIn(), FoodCatalogSpecs.categoryNotIn()을 적용한다. 그런데 applyRuntimeGate()는 같은 조건을 (!restrictions.foodIds().contains(), !restrictions.categories().contains()) 메모리에서 다시 필터링한다.

두 레이어 중 어느 쪽이 "진짜" 필터인지 읽는 사람이 판단해야 한다. DB Spec을 제거하면 메모리 필터가 백업이 되고, 메모리 필터를 제거하면 DB Spec만 남는다. 현재 코드에서는 의도가 불명확하다.

명시적 의도가 없으면 유지보수 부담
나중에 DB Spec 필터를 최적화 이유로 제거하면, 메모리 필터만 남아 있을 때 왜 있는지 알 수 없다.
현재 — 양쪽에 동일한 조건
// DB에서 (loadCatalogCandidates)
spec = spec.and(FoodCatalogSpecs.idNotIn(restrictions.foodIds()));
spec = spec.and(FoodCatalogSpecs.categoryNotIn(restrictions.categories()));

// 메모리에서 (applyRuntimeGate) ← 동일 조건 재적용
.filter(food -> !restrictions.foodIds().contains(food.getId()))
.filter(food -> !restrictions.categories().contains(food.getCategory()))

최우선 권장
#1 strictAllergyMode 연결부터 수정

이 버그는 알러지 사용자의 추천 게이트 정책이 의도대로 작동하지 않는다는 것을 의미한다. 수정 범위는 좁다 — CandidateRestrictions 레코드에 boolean strictAllergyMode를 추가하고 applyRuntimeGate()에서 allergenGate.passesGate(..., strictMode)를 호출하면 된다. 이미 AllergenConfidenceGate는 준비되어 있다.

이 수정이 끝난 뒤 #2 알러젠 게이트 통합을 탐색할 것을 권장한다. 두 게이트를 AllergenSafetyGate 하나로 묶으면 CandidatePool의 테스트 복잡도가 크게 줄어들고, 향후 신뢰도 정책 변경(예: RECIPE_DERIVED 처리)을 한 곳에서 관리할 수 있다.

#3 (중복 필터)는 기능 오류가 아니므로 sprint 내 리팩터링 여유가 있을 때 처리.
기존 ADR과의 충돌 여부

이 리포트의 후보들은 기존 ADR-0002 (목표별 영양 최적화)나 알러젠 관련 정책 결정과 충돌하지 않는다. #1은 기존 정책을 올바르게 구현하기 위한 버그 수정이고, #2는 동일한 정책을 더 깊은 모듈 경계 안에 캡슐화하는 리팩터링이다.
