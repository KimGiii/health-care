1. 식단 추천 후보 풀 Module 깊이 만들기

추천 적합성 게이트가 얕은 Specification과 Engine 안전망에 나뉘어 있음.

Strong in-process

Files

  • FoodCatalogSpecs.java
  • DailyDietRecommendationUseCases.java
  • DietRecommendationEngine.java
  • DailyDietRecommendationUseCasesTest.java

Problem

추천 후보 Interface가 Specification, Sort, 제한 조건 분해, Engine의 중복 필터로 흩어져 있어 추천 적합성 게이트의 Implementation이 새고 있다.

Solution

식단 추천 후보 풀을 deep Module로 세우고 JPA Specification, 상태 필터, 제한 조건 필터, 알러젠 태그 조회를 그 Implementation 안으로 숨긴다.

Benefits

  • locality: 게이트 규칙 한 Module
  • leverage: UseCase Interface 축소
  • tests: Specification mocking 제거
  • 검색/추천 정책 분리 선명

Before

UseCases: restrictions 분해
FoodCatalogSpecs: status, calories
Repository: Specification + Sort
Engine: calories, food, category safety filter
Interface가 Implementation 순서를 알아야 함

After

UseCases: 사용자와 목표 계산
식단 추천 후보 풀 Module
추천 적합성 게이트
제한 조건 Adapter
알러젠 태그 Adapter
Engine: 끼니 구성

2. 추천 큐레이션 오류 모드를 한 Seam에 모으기

RecommendationCuration은 좋은 시작이지만 입출력 Adapter가 아직 각자 규칙을 만진다.

Strong local-substitutable

Files

  • RecommendationCuration.java
  • FoodCatalog.java
  • RecommendedFoodEntry.java
  • BrandMenuCsvImporter.java
  • FoodCatalogIngestService.java

Problem

RECOMMENDABLE_WITH_CAUTION과 reason의 불변 조건은 값 객체에 들어갔지만, CSV Adapter, JPA row 재구성, 응답 DTO가 각자 큐레이션을 해석한다.

Solution

추천 큐레이션 Module의 Interface를 입출력 Adapter가 모두 통과하는 단일 Seam으로 만들고, DB 불량 상태의 오류 모드를 그 Module 안에서 명시한다.

Benefits

  • locality: caution 정책 한곳
  • leverage: 적재와 응답 공통 검증
  • tests: 오류 모드 직접 검증
  • 운영 데이터 장애 반경 축소

3. DietRecommendationEngine Interface 줄이기

Engine이 필터링, 알러젠 신뢰, rotation, DTO 생성까지 함께 알고 있다.

Worth exploring in-process

Files

  • DietRecommendationEngine.java
  • RecommendedFoodEntry.java
  • AllergenConfidenceGate.java
  • DailyDietRecommendationUseCases.java

Problem

Engine Interface가 FoodCatalog, DietRestriction, FoodAllergenTag, strictMode를 그대로 요구해 호출자가 Implementation 세부 지식을 알아야 한다.

Solution

추천 후보 필터링과 끼니 구성 사이의 Seam을 선명히 하고, Engine은 이미 추천 가능한 후보로 끼니를 구성하는 deep Module로 좁힌다.

Benefits

  • interface shrinks
  • implementation absorbs DTO details
  • locality: 끼니 구성 테스트
  • leverage: 후보 정책 교체 가능

Before mass

Interface: targets, mealTypes, FoodCatalog, DietRestriction, tagsByFoodId, strictMode, date
Implementation: filtering, confidence, rotation, serving, DTO
Interface가 Implementation의 절반을 설명함

After mass

Interface: 목표, 끼니, 추천 가능한 후보
Implementation: rotation, serving, category balance, output facts
더 깊은 Module, 더 작은 test surface

4. 식품 카탈로그 적재 정규화 Module 확장

upsert 정책은 모였지만 row 변환 지식은 여러 importer에 남아 있다.

Worth exploring ports & adapters

Files

  • BrandMenuCsvImporter.java
  • StandardFoodCatalogImporter.java
  • MfdsFoodNutrientDbImporter.java
  • FoodCatalogIngestService.java
  • FoodCatalogIdentity.java

Problem

숫자/날짜/제공량/카테고리 정규화가 source별 importer Implementation에 반복된다. 새 Adapter가 생기면 같은 지식이 다시 퍼진다.

Solution

source별 Adapter는 원본 row 해석만 맡고, 식품 카탈로그 적재 정규화 Module이 공통 변환과 검증을 흡수한다.

Benefits

  • locality: 변환 규칙 한곳
  • leverage: 데이터원 추가 비용 감소
  • identity Seam과 변환 Seam 분리
  • importer tests 작아짐

Before cross-section

Brand CSV: parseDouble, parseDate, category, serving
Standard food: parseDouble, parseDate, category, serving
MFDS nutrient: parseDouble, parseDate, category, serving
FoodCatalogIdentity: source code, duplicate key
FoodCatalogIngestService: upsert

After cross-section

Source Adapters: raw row semantics
식품 카탈로그 적재 정규화 Module
number, date, serving, category, nutrition basis
FoodCatalogIdentity: identity Seam
FoodCatalogIngestService: persistence Seam

5. seed 큐레이션 검증을 운영 데이터 Module로 올리기

V25 allowlist는 SQL과 regex 테스트에 머물러 있어 운영 정책의 Interface가 약하다.

Speculative mock

Files

  • V25__seed_recommendation_curation.sql
  • FoodCatalogSeedCurationMigrationTest.java
  • docs/exec-plans/FOOD_CATALOG_ENRICHMENT.md

Problem

seed 추천 가능 후보 수와 카테고리 최소 기준이 SQL 문장과 regex 테스트에 묶여 있어, 운영 검수 정책을 재사용할 Interface가 없다.

Solution

seed 큐레이션 데이터를 독립적인 운영 데이터 Module로 다루고, migration은 그 데이터를 반영하는 Adapter로 낮춘다.

Benefits

  • locality: 후보 수 기준 한곳
  • leverage: 운영 검증 재사용
  • tests: SQL parsing 감소
  • 데이터 보강 흐름 선명

Top recommendation

먼저 식단 추천 후보 풀 Module을 깊게 만든다.

Phase 4의 핵심 계약은 "추천 후보는 전체 식품 카탈로그가 아니다"입니다. 이 계약이 현재 UseCase, Specification, Engine에 나뉘어 있으므로, 이 Module을 깊게 만들면 추천 큐레이션, 알러젠 회피, 후보 부족 테스트의 locality와 leverage가 가장 크게 좋아집니다.
