Problem

브랜드 공식 메뉴 CSV의 필수값, 길이 제한, row 실패 이유가 Importer Implementation 안에 묻혀 있고 Interface는 결과 카운트만 준다.

Solution

브랜드 공식 메뉴 입력 계약을 하나의 deep Module로 세워 CSV 계약, field envelope, row 거절 근거를 한 곳에 모은다.

Benefits

  • Locality: 입력 규칙 집중
  • Leverage: 운영 검수 재사용
  • DB 실패 전 검증
  • Tests hit one Interface

Problem

세 Importer Module이 비슷한 normalize, parse, date, category, upsert Implementation을 반복한다.

Solution

소스별 Adapter는 원본 row를 식품 카탈로그 적재 사실로 바꾸고, 공통 ingest Module이 검증과 upsert를 맡는다.

Benefits

  • Locality: upsert 규칙 집중
  • Leverage: 세 Adapter 공유
  • Depth: Interface 축소
  • 중복 테스트 제거

한 deep Module이 검색, 중복 리포트, 적재의 동일성 Leverage를 만든다.

Problem

브랜드명은 적재에만 쓰이고 중복 후보 리포트는 식품명만 본다. phase 5 검색 정리에서 같은 규칙이 또 생길 가능성이 높다.

Solution

식품 카탈로그 동일성 계산을 하나의 Module로 집중시키고, 적재·중복·검색이 같은 개념을 공유하게 한다.

Benefits

  • Locality: 이름 규칙 집중
  • Leverage: phase 5 재사용
  • false duplicate 감소
  • 검색 품질 테스트 집중

Top recommendation

Start with the brand official menu import contract.

phase 3의 직접 산출물이고, 운영자가 만지는 CSV 입력의 오류가 DB 저장 실패나 조용한 skip으로 나타날 수 있다. 이 Module을 deep하게 만들면 이후 공공데이터 ingest 통합도 더 작게 진행된다.
