Problem. 위반 탐지와 6개 지표 누적이 runner 한 루프에 엉켜 있고, report는 위치 기반 7-int라 호출부가 new Report(6,5,8,1,1,15,0) 매직 튜플이 된다.

Solution. runner가 시나리오마다 ScenarioOutcome(명명된 위반)을 내고, report는 outcome 목록의 fold로 만든다.

  • · locality: 위반 규칙이 한 모듈에 모임
  • · interface는 시나리오 1건의 outcome
  • · 매직 7-int 튜플 제거
  • · Phase 3 새 엔진도 같은 outcome 재사용

RemainingNutritionBudget

Problem. 두 record가 한 음절(Nutrient/Nutrition)만 다르고 역할은 "1종 vs 4종 묶음"이라 navigability가 떨어진다.

Solution. per-nutrient를 NutrientBudget로 바꾸고 묶음 record 안에 중첩한다. CONTEXT.md "남은 영양량" 정의와도 일치.

  • · 이름이 포함 관계를 표현
  • · 호출부 혼동 제거
  • · 사용처 적어 비용 낮음 (2 파일)

Problem. 칼로리·단백질·탄수·지방 4-tuple이 NutritionTargets(int)와 NutritionVector(double) 두 곳에 있고, runner가 둘 사이를 손으로 환산한다.

Solution. 목표·섭취·정책이 함께 표현할 공유 Nutrients 값을 두되, NutritionTargets는 기존 영양 목표 도메인에서 널리 쓰이므로 Phase 2 데이터 계약 작업과 함께 신중히 수렴시킨다.

  • · leverage: 한 4-tuple, 여러 호출부
  • · int/double 환산 leakage 제거
  • · 단, 기존 dto 파급 범위 큼 → Phase 2와 병행

D. 정책 "버전"이 라벨일 뿐 seam이 아니다

Speculative strategy seam
  • nutrition/policy/GoalAwareNutritionPolicy.java

지금 — 비율은 private 상수, 버전은 문자열 1개, 분기는 in-place switch

CURRENT_VERSION = "2026-06-18.v1"
VERIFIED_CALORIE_UPPER_RATIO = 0.98 … (private static final ×6)
resolve(): switch(goalType){ … } ← v2는 이 자리를 직접 수정
⚠ ADR-0002 §2 / 계획 §3와 긴장. 문서는 "비율은 코드 상수가 아니라 버전이 있는 정책으로 관리한다"고 명시했지만, 현재는 비율이 클래스 private 상수로 흩어져 있고 버전은 문자열 라벨뿐이다. 다만 지금은 버전이 v1 하나뿐 — adapter 1개는 가설적 seam이라 registry를 미리 만들 필요는 없다. v2를 추가하는 순간 같은 switch를 in-place 수정하게 되므로, 그때 버전을 데이터 seam으로 분리하는 것을 권한다.

권장. 지금 구조 변경은 YAGNI. v2 정책 추가 시점에 "정책 버전 = 비율 데이터"로 분리하면 두 번째 adapter가 seam을 정당화한다.
