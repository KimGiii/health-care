# 로컬 식품 카탈로그의 식단 추천 활용성 평가

- 작성일: 2026-08-03
- 조사 대상: 로컬 PostgreSQL `healthcare_local` (`localhost:5433`)
- 조사 방식: 읽기 전용 SQL 실사, 추천 도메인 코드 및 제품 문서 검토
- 검토 관점: 영양학, 실무 식단 관리, 추천 데이터·알고리즘 감사

## 1. 결론

현재 데이터는 **알레르기가 없는 사용자를 대상으로 열량과 단백질·탄수화물·지방 목표에 맞는 식품 조합을 제한적으로 추천**하는 데 사용할 수 있다. 다만 전체 620,120건을 추천에 직접 쓰면 안 되며, 현재와 같이 검수 상태·대표 레코드·영양 완결성·검증 제공량을 통과한 curated pool만 사용해야 한다.

운영 DB 기준 런타임 추천 가능 식품은 11,979건이지만, 이 중 9,079건(75.8%)이 `PROCESSED`이다. 반면 곡류·채소·과일은 0건이다. 원인은 균형 식단에 유용한 `SEED` 300건에 검증된 제공량 옵션이 없어 런타임 hard filter에서 전부 제외되기 때문이다. 따라서 현재 수치 최적화만으로는 가공식품 위주의 비현실적인 식사가 생성될 위험이 높다.

알레르기 사용자는 유효한 완결 프로필이 있는 최대 326건만 통과할 수 있고, 이 풀도 가공식품에 크게 편중되어 있다. fail-closed 정책은 유지하되, 알레르기 추천을 일반 출시 수준으로 간주해서는 안 된다.

가장 먼저 해야 할 일은 다음 세 가지다.

1. 균형 식단용 기본 식품에 검증된 제공량을 추가해 곡류·단백질원·채소·과일 풀을 복구한다.
2. 단순 점수 순위가 아니라 식품군 역할을 갖는 끼니 템플릿으로 조합한다.
3. 나트륨·식이섬유·당류·포화지방과 알레르기 근거의 완결성을 단계적으로 강화한다.

`SEARCH_ONLY` 604,676건을 추천 대상으로 자동 승격해서는 안 된다. 검색·기록용 카탈로그와 추천용 curated pool을 분리한 현재 방향이 적절하다.

`SEED`의 추천 상태 식품 300건에는 제공량 옵션이 하나도 없다. 흰쌀밥, 현미밥, 고구마, 닭가슴살, 달걀, 두부, 브로콜리, 과일처럼 식단의 골격이 될 항목이 DB에는 있지만 추천에서는 쓰이지 않는다.

전체 제공량 옵션은 1,323,064개이고 모두 `OFFICIAL_SERVING`이며 검증일이 있다. 중량 범위는 3~600g이다. 이 값은 데이터상 유효하더라도 식품 역할에 따라 현실성이 달라지므로 역할별 최소·최대량 검사가 추가로 필요하다.

### 2.3 영양 데이터 품질

| 결측 항목 | 전체 결측 건수 | 비고 |
|---|---:|---|
| 단백질 | 21 | 낮음 |
| 탄수화물 | 26,608 | 추천 후보에서는 완전 |
| 지방 | 27,780 | 추천 후보에서는 완전 |
| 당류 | 2,904 | 일부 품질 판정 제한 |
| 나트륨 | 1,972 | 대체로 사용 가능 |
| 식이섬유 | 592,285 | 현재 최적화에 사실상 사용 불가 |
| 제공량 기준값 | 106,121 | 옵션 테이블과 별도 관리 필요 |

전체 식품 중 24,678건은 표시 열량과 단순 Atwater 환산값의 차이가 `max(50 kcal, 표시 열량의 30%)`를 넘었다. 알코올, 식이섬유, 유기산, 반올림 등 정당한 예외가 있으므로 자동 삭제 기준으로 쓰면 안 되지만, 검수 우선순위 플래그로는 유용하다. 1,550건은 개별 영양값이 100g을 초과하는 등 단위·기준량 검토가 필요한 이상치 후보였다.

현재 엔진이 최적화하는 값은 열량과 P/C/F다. 따라서 ‘목표 매크로에 맞음’은 말할 수 있지만, ‘영양적으로 균형 잡힘’이나 ‘저염·고섬유질’이라고 표현하면 안 된다.

### 2.4 중복과 사용 신호

- `CANONICAL`: 325,323건
- `SUPERSEDED`: 289,053건
- `COLLISION`: 5,744건
- 추천 파이프라인은 `canonical_group_id`가 있는 비대표 식품을 제외한다.
- 의미가 충돌한 `COLLISION`은 수동 검토가 계속 필요하다.
- `usage_count > 0`인 식품은 10건, 총 사용도 10회 수준이라 인기도 학습의 근거가 되기 어렵다.

개인화 신호는 안전·영양 hard gate 뒤의 약한 순위 신호로만 사용해야 한다. 노출이 충분히 쌓이기 전 raw count를 직접 비교하지 말고 최소 노출 기준 또는 Bayesian smoothing을 적용해야 한다.

## 3. 알레르기 안전성

| 항목 | 현황 |
|---|---:|
| 알레르기 태그 | 1,059개 |
| 태그가 있는 식품 | 367건 |
| 유효 완결 프로필 | 326건 |
| `DIRECT_VERIFIED` | 24건 |
| `LABEL_DERIVED` | 302건 |

알레르기 제한이 있으면 현재 `AllergenSafetyGate`는 유효한 완결 프로필이 없는 식품을 차단한다. 이 fail-closed 정책은 옳다. 다만 최대 풀 326건은 전체 canonical 추천 후보의 2.65%이며, 그중 약 85.6%가 가공식품이다. 제한 태그를 적용하면 후보는 더 줄어든다.

현재 스키마는 제품 문서가 요구하는 `CONTAINS`와 `MAY_CONTAIN`, 근거별 버전, 충돌 판정을 충분히 표현하지 못한다. 다음 조건을 만족하기 전에는 의료급 안전을 암시하거나 알레르기 추천의 폭넓은 가용성을 주장하면 안 된다.

- 한국 표시 대상 알레르겐 전체 검토 범위 저장
- 포함/교차접촉 관계 분리
- 출처·원문·버전·검토일·유효기간 보존
- 근거 충돌 시 자동 제외 및 재검수
- 목표·끼니 수·제한 태그 조합별 후보 충분성 검증

## 4. 현재 데이터로 가능한 것과 불가능한 것

### 가능한 것

- 알레르기가 없는 사용자의 남은 일일 열량과 P/C/F 범위에 맞춘 결정적 조합
- 명시한 식품·카테고리·키워드 기피 조건의 hard exclusion
- canonical·신선도·추천 상태·검증 제공량 기반 안전한 데이터 계약
- 최근 7일 반복 회피와 최근 30일 기록/새로고침 신호를 이용한 제한적 soft ranking
- 추천 실패 이유 표시와 추천→기록 전환 측정

### 조건부 가능한 것

- 알레르기 사용자의 추천: 326개 검증 풀 안에서는 fail-closed로 가능하지만, 실제 식단 구성 가능성은 사용자 조건별로 별도 검증해야 한다.
- 나트륨·당류·포화지방 품질 반영: 데이터 완결성이 확보된 부분집합에서만 가능하다.

### 현재 불가능하거나 금지해야 하는 것

- 질환 치료식, 임신·수유·소아·신장질환·당뇨·섭식장애용 자동 처방
- 의료급 알레르기 안전 보증
- 미량영양소가 균형 잡힌 식단이라는 주장
- 레시피, 조리법 또는 완결 메뉴로의 해석
- 가격·재고·계절성·보유 식재료를 반영한 추천
- 신뢰할 만한 학습 기반 개인화 품질 주장

## 5. 권장 추천 방식

### 5.1 후보 hard gate

다음 순서는 상쇄 불가능한 통과 조건으로 유지한다.

1. 활성 + canonical 대표
2. 추천 가능 상태
3. 출처별 신선도
4. 목표에 필요한 영양 완결성
5. 검증된 현실적 제공량
6. 사용자의 식품·카테고리·키워드 제한
7. 알레르기 근거 완결성·유효성·충돌 없음
8. 선택한 끼니 수에서 목표 범위 달성 가능

안전 점수를 다른 장점으로 상쇄해서는 안 된다. 안전은 pass/fail이고, 품질 점수는 통과 후보 사이의 순위에만 쓴다.

### 5.2 끼니 템플릿

단순히 점수가 높은 식품 3개를 고르지 말고 역할 슬롯을 채운다.

| 끼니 | 기본 슬롯 |
|---|---|
| 아침 | 곡류 + 단백질/유제품 + 과일 |
| 점심·저녁 | 곡류 + 단백질원 + 채소 |
| 간식 | 과일·유제품·견과·단백 간식 중 1~2개 |

`PROCESSED`, `BEVERAGE`, `FAT`, `OTHER`는 기본 슬롯의 주역이 아니라 보조·교체 슬롯으로 제한한다. 후보가 부족하면 가공식품으로 조용히 대체하지 말고, ‘균형 식품군 후보 부족’을 실패 또는 품질 저하 사유로 표시한다.

### 5.3 제공량

- 공식 제공량을 우선한다.
- 화면에는 `150g · 1공기`, `100g · 1팩`처럼 g과 생활 단위를 함께 표시한다.
- 조절은 가급적 `0.5배 / 1배 / 1.5배` 단계로 제한한다.
- 식용유·소스, 주식, 단백질 식품, 채소 등 역할별 허용 범위를 둔다.
- 3g·600g 같은 극단값은 역할별 범위를 벗어나면 추천 제외 또는 검수 대상으로 보낸다.

### 5.4 품질 순위

hard gate 통과 후 다음 비중을 초기 가설로 사용한다.

| 요소 | 가중치 |
|---|---:|
| 목표 영양 범위의 중심 거리 | 35% |
| 끼니별 목표 열량 비율 오차 | 15% |
| 단백질 분배 적합성 | 15% |
| 식품군 다양성 | 10% |
| 최근 7~14일 반복 회피 | 10% |
| 선호·기록 전환 | 10% |
| 데이터·제공량 신뢰도 | 5% |

현재 `proteinSourceOccupancyPenalty`는 단백질원을 여러 끼니에 포함할수록 불리하게 작동할 가능성이 있어 단백질 분산 목표와 반대인지 검증해야 한다. `mealCalorieVariance`도 아침 25%·점심 35%·저녁 30%·간식 10%의 의도적 비대칭 목표와 충돌하지 않도록, 단순 분산 대신 끼니별 목표 비율 오차를 써야 한다.

## 6. 데이터 보강 우선순위

### P0: 추천 가능한 균형 식품 풀 복구

- `SEED` 300건 중 추천 대상에 검증 제공량 2~4개를 추가한다.
- 쌀밥·잡곡·감자·고구마, 달걀·두부·콩·생선·살코기, 채소·나물, 과일, 무가당 유제품을 우선한다.
- 조리 전/후, 생/건조, 가식부, 100g 기준을 이름과 메타데이터에 명시한다.
- 추천 승격 계약에 P/C/F/열량 + 제공량 + 출처·검증일을 필수로 둔다.
- 고염 가능 식품은 나트륨, 가공·음료·유제품은 당류와 포화지방이 없으면 `SEARCH_ONLY`를 유지한다.

### P1: 건강 품질과 알레르기 근거

- 나트륨 상한, 식이섬유 하한, 당류·포화지방 penalty를 도입한다.
- 식품군 최소 커버와 가공식품 비중 상한을 적용한다.
- 알레르기 프로필을 식품군 균형 있게 최소 수천 건으로 확대한다.
- `CONTAINS`/`MAY_CONTAIN`, 근거 버전 및 충돌 판정을 구현한다.
- 영양값 nonnegative, 당류≤탄수화물, 포화+트랜스지방≤지방 같은 QC 규칙을 허용 오차와 함께 추가한다.

### P2: 개인화와 UX

- 좋아함/싫어함, 조리 시간, 예산, 식사 장소, 보유 식재료, 채식·종교 조건, 매운맛, 반복 허용도를 입력받는다.
- 알레르기와 의학적 제한은 hard, 기호·비용·시간은 soft preference로 다룬다.
- 한 항목 교체, 분량 ±단계, 오늘만 제외/항상 제외, 실제 섭취량 수정 기능을 제공한다.
- 추천 이유로 남은 단백질, 최근 미섭취, 제한 통과, 데이터 근거와 검증일을 표시한다.

## 7. 출시 및 평가 단계

1. **데이터 계약 고정**: 12,279 canonical 추천 후보와 11,979 런타임 후보의 일일 스냅샷, 카테고리 분포, 이상치 대시보드를 만든다.
2. **비알레르기 제한 베타**: 템플릿, 제공량 범위, 식품군 다양성, 단백질 분배를 먼저 검증한다.
3. **알레르기 제한 베타**: 검증 풀 확대와 근거 모델 구현 후, 태그별 feasibility sweep을 통과한 범위에서만 연다.
4. **개인화 튜닝**: 충분한 노출·기록 이벤트가 쌓인 후 가중치를 A/B 검증한다.
5. **보조 영양소 도입**: 영양소별 완결성과 출처 기준을 달성한 뒤 독립적으로 활성화한다.

### 핵심 지표

- 안전: 알레르겐·기피·만료·비canonical·불완전 매크로·미검증 제공량 위반 0건
- 가능성: 목표/끼니 수/제한 수/알레르겐별 추천 성공률, 후보 풀 p10/p50, true infeasible와 탐색 한도 실패 분리
- 영양 품질: 목표 범위 위반 0, 목표 중심 거리, 끼니별 단백질 분배, 식품군 수, 가공식품 비율, 7/14일 반복률
- 제품: 노출→기록 전환율, 다시 추천률, 교체 후 기록률, 추천 기록 삭제·수정률
- 운영: 응답 p95, 검수 큐 크기, 데이터 버전 만료율, collision 해소율

## 8. 로컬 환경 일관성 주의

별도 테스트 DB `healthcare_test`에는 `SEED` 300건만 존재하며, `RECOMMENDABLE` 42건에도 제공량 옵션이 없어 실제 추천 가능 후보가 0건인 상태가 관찰됐다. 개발 DB `healthcare_local`과 테스트 DB의 fixture가 크게 달라 테스트가 운영형 데이터 편향과 알레르기 후보 고갈을 대표하지 못한다.

다음 fixture 계층을 분리하는 것이 좋다.

- 빠른 단위 테스트용 최소 fixture
- 카테고리·제공량·알레르기 경계를 재현하는 통합 fixture
- 운영 분포를 익명 집계로 재현하는 benchmark snapshot
