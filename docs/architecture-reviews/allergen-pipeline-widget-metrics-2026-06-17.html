Candidate 1

BrandMenuCsvImporter — 알러젠 교체 로직의 깊이 부족

Strong
Files
BrandMenuCsvImporter.java FoodAllergenTagRepository.java AllergenDataSource.java V31__brand_official_allergen_source.sql
Problem

BrandMenuCsvImporter가 CSV 파싱, 한글 라벨→AllergenTag 매핑, DB 교체(deleteAllByFoodCatalogIdAndSource → saveAll), 신뢰도 판정, 검증을 모두 한 클래스 안에서 처리한다. 특히 삭제 후 재삽입 사이클이 임포터 안에 하드코딩돼 있어, 같은 "브랜드 공식 알러젠 교체" 로직이 미래에 다른 임포터에서 필요할 때 복붙이 불가피하다.

🔍 삭제 테스트: replaceBrandOfficialAllergenTags()를 삭제하면 복잡성이 CSV 임포터 하나에서 사라지는 게 아니라 미래 임포터들로 분산된다. → 레버리지가 있다.

Solution

FoodAllergenTagRepository에 replaceBySource(foodCatalogId, source, tags) 메서드를 추가해 "특정 소스의 알러젠 태그 전량 교체" 책임을 리포지터리 인터페이스 뒤로 숨긴다. 임포터는 어떤 태그가 들어가야 하는지만 알면 되고, 어떻게 저장되는지는 모른다.

✅ Locality 향상: 교체 로직 버그가 하나의 리포지터리 메서드에 집중됨. KHANES·FOODQR 임포터가 추가돼도 동일 메서드 재사용.

Before — 얕음
BrandMenuCsvImporter
├ CSV 파싱 & 행 검증
├ 한글 알러젠 라벨 매핑
├ FoodCatalogIngestService.ingest()
├ deleteAllByFoodCatalogIdAndSource() ← 직접 호출
├ saveAll(새 태그들) ← 직접 조합
└ 완결 플래그 저장
FoodAllergenTagRepository: delete + saveAll 노출
After — 깊어짐
BrandMenuCsvImporter
├ CSV 파싱 & 행 검증
├ 한글 알러젠 라벨 매핑
├ FoodCatalogIngestService.ingest()
└ repository.replaceBySource(id, BRAND_OFFICIAL, tags)
FoodAllergenTagRepository
└ replaceBySource() — delete+insert 트랜잭션 캡슐화
미래 KHANES 임포터도 동일 메서드 재사용 가능
Tests 개선

현재: BrandMenuCsvImporterTest가 실제 DB 없이는 알러젠 교체를 검증하기 어려움. 리포지터리에 replaceBySource() 세움 → 임포터 테스트에서 mock 1개로 교체 동작을 단언 가능. 리포지터리는 슬라이스 테스트(@DataJpaTest)로 독립 검증.

Candidate 2

AllergenDataSource + DB CHECK 제약 — 숨겨진 결합

Worth Exploring
Files
AllergenDataSource.java V31__brand_official_allergen_source.sql V29__allergen_tags.sql (추정)
Problem

AllergenDataSource enum에 새 값(BRAND_OFFICIAL)을 추가할 때 반드시 Flyway 마이그레이션도 함께 수정해야 한다는 제약이 코드 어디에도 명시돼 있지 않다. 오늘 V31이 정확히 이 작업을 했지만, 다음 개발자가 enum만 추가하고 마이그레이션을 빠뜨리면 런타임 DataIntegrityViolationException이 발생한다.

DB CHECK 제약이 Java 타입 시스템 밖에 있어서 컴파일 타임에 잡히지 않는다.

Solution

옵션 A (단순): 마이그레이션 파일에 주석으로 "이 CHECK는 AllergenDataSource enum과 동기화돼야 함" 경고 추가.

옵션 B (심층): CHECK 제약을 제거하고 JPA @Enumerated(EnumType.STRING)만 신뢰. enum이 유일한 진실 소스가 된다. DB 측 검증을 포기하는 트레이드오프.

옵션 C (강건): 통합 테스트에서 enum 값 목록과 DB CHECK 제약 값 목록을 비교해 불일치를 컴파일 대신 테스트 시점에 잡는다.

현재 — 암묵적 결합
AllergenDataSource.java
  + BRAND_OFFICIAL ← 코드 추가
↕ 동기화 강제 없음
V31__brand_official_allergen_source.sql
  + CHECK(..., 'BRAND_OFFICIAL') ← 수동 추가

⚠ 둘 중 하나만 수정하면 런타임 오류
옵션 C — 테스트 시점 검증
AllergenDataSourceSyncTest.java
  // DB CHECK 값 목록 조회
  // AllergenDataSource.values() 비교
  assertThat(dbValues).containsExactlyInAnyOrder(
    javaEnumNames
  );

✅ CI가 불일치를 빌드 실패로 잡음
Candidate 3

GoalWidgetSnapshot — 하위호환성 decoder가 모델 안에 있음

Worth Exploring
Files
WidgetSnapshot.swift GoalWidget.swift
Problem

GoalWidgetSnapshot.init(from decoder:)가 구 필드 recentWeights를 신규 metricPoints로 변환하는 마이그레이션 로직을 포함한다. 이 로직이 모델 init 안에 있어서:

  • 단독으로 단위 테스트하기 어렵다
  • "구 포맷 언제까지 지원?"이라는 정책이 코드에 안 보인다
  • 세 번째 포맷 변경 시 init 이 더 복잡해진다
Solution

하위호환성 변환을 static func migrate(from legacy: LegacyGoalSnapshot)처럼 명시적 정적 메서드로 분리한다. init(from decoder:)는 현재 포맷만 디코딩하고, 구 포맷 감지 로직은 별도 함수에 둔다.

✅ 마이그레이션 함수를 독립적으로 테스트 가능. 구 포맷 지원 종료 시 함수 하나만 삭제.

Before — init에 마이그레이션 혼재
GoalWidgetSnapshot {
  init(from decoder:) {
    // 1. 현재 포맷 시도
    // 2. 실패 시 recentWeights 읽기
    // 3. MetricPoint로 변환
    // 마이그레이션 + 파싱 혼재 ⚠
  }
}
After — 관심사 분리
GoalWidgetSnapshot {
  init(from decoder:) { /* 현재 포맷만 */ }
  
  static func migrate(
    legacy: LegacyFormat
  ) -> GoalWidgetSnapshot { /* 변환만 */ }
}
// 호출부: 디코딩 실패 시 migrate() 호출

HealthCareWidgets 새 타겟 — 목적이 불분명한 레이어

Speculative
Files
HealthCareWidgets/HealthCareWidgets.swift HealthCareWidgets/HealthCareWidgetsBundle.swift ios/project.yml
Problem

기존 HealthCareWidget 타겟(칼로리·목표·스트릭 위젯 포함)이 있는데, 오늘 HealthCareWidgets라는 새 타겟이 추가됐다. 현재는 Xcode boilerplate stub만 존재한다.

  • 두 타겟이 같은 App Group을 쓸지 별도 App Group을 쓸지 불분명
  • 기존 위젯들을 이 타겟으로 이전할 계획인지, 별도 위젯을 추가할 계획인지 불분명
  • stub을 배포하면 위젯 갤러리에 빈 위젯이 노출될 위험
Solution

두 가지 명확화 질문:

A. 기존 3개 위젯을 이 새 타겟으로 통합할 계획이라면, 마이그레이션 계획을 ADR로 기록하고 stub을 배포 전에 제거하거나 #if DEBUG로 감싼다.

B. 완전히 새 종류의 위젯(예: Live Activity, Control Widget)을 위한 타겟이라면 타겟 이름을 의도를 드러내도록 변경한다.

현재 상태 — 두 타겟, 목적 불분명

즉시 효과

Locality

노력 대비 효과
