FoodCatalogService · BrandMenuCsvImporter · StandardFoodCatalogImporter

Before — normalize() 3곳 분산

After — 단일 seam으로 통합

Problem

normalize()가 세 모듈에 분산 정의 — 정규화 규칙 변경이 3곳 수정을 요구한다.

Solution

Wins

  • · locality: 정규화 버그가 한 모듈에 집중
  • · leverage: N 호출 측이 동일 구현 공유
  • · interface 면적 감소
  • · 중복 normalize 메서드 삭제
Worth exploring depth · testability

BrandMenuCsvImporter 검증 파이프라인 심화

BrandMenuCsvImporter (392줄) · FoodCatalogImportRejectedRow

Before — toFoodCatalog()에 6단계 인라인

toFoodCatalog(row) — 392줄
필수값 null 검사 (4개 필드)
숫자 형식 검증 (8개 필드)
음수 검증 (7개 필드)
제공량 관계 검증 (2개 규칙)
필드 길이 검증 (5개 필드)
큐레이션 검증 (1개 규칙)
각 단계가 독립 early-return → 순서가 암묵적

After — 명시적 검증 체인

BrandMenuValidationPipeline
validate(row): Result<FoodCatalog>
RequiredFields.check()
NumericFormat.check()
NonNegative.check()
ServingSize.check()
FieldLength.check()
Curation.check()
각 단계 독립 단위 테스트 가능

Problem

6단계 검증이 toFoodCatalog()에 인라인. 순서가 암묵적이고, 각 단계를 단독으로 테스트하는 seam이 없다.

Solution

검증 단계를 명명된 객체로 추출. BrandMenuValidationPipeline이 단일 interface로 체인을 감싼다.

Wins

  • · 검증 순서가 interface에서 명시됨
  • · 각 단계를 개별 단위 테스트 가능
  • · 새 필드 추가 시 파이프라인 1곳만 수정
  • · locality: 검증 버그 집중화
Worth exploring depth · extensibility

Solution

Wins

  • · locality: 정책 결정이 한 모듈에 집중

깊이를 이미 확보한 모듈들

RecommendationCuration (sealed)

sealed interface + pattern matching이 WithCaution만 reason을 강제. 타입 시스템이 불변 조건을 보장한다.

✓ null 불가 ✓ 타입 안전 switch ✓ deep

FoodCatalogIdentity

3개 정적 메서드 뒤에 NFC 정규화 + 공백 축약 + 특수문자 제거 구현. 순수 함수형 → 테스트가 직접 통과한다. seam이 필요 없다.

✓ 순수 함수 ✓ 멱등성 ✓ deep

FoodCatalogIngestCandidate (값 객체)

accepted / rejected / skipped 상태를 단일 타입으로 표현. Importer ↔ IngestService 간 interface가 명확하다.

✓ 상태 명시 ✓ 구조화 거절 사유

source + food_code 유일성

DB 레벨 unique 인덱스가 멱등 upsert를 보장. 배치 재실행이 안전하고, 추천 상태 정책이 one source of truth를 갖는다.

✓ 멱등성 ✓ DB 보장

정규화 로직을 FoodCatalogIdentity 모듈로 통합

세 모듈에 흩어진 normalize()를 FoodCatalogIdentity.normalizeInput()으로 통합하는 작업은 가장 작은 변경으로 가장 큰 locality 이득을 준다. 이미 FoodCatalogIdentity가 deep 모듈로 설계되어 있으므로, seam을 새로 만들 필요 없이 기존 interface를 확장하는 것으로 충분하다.
