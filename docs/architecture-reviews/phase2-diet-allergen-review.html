관련 파일

domain/nutrition/policy/NutrientCompletenessPolicy.java

⚠ 문제

isComplete(GoalType goalType, DietRecommendationCandidate candidate)는 goalType 파라미터를 완전히 무시하고 candidate.macroDataComplete()만 반환합니다. 인터페이스(2개 파라미터, GoalType enum + 후보 객체)가 구현(1줄 불리언 위임)보다 훨씬 복잡합니다. Deletion test: 이 클래스를 삭제하고 호출부에서 candidate.macroDataComplete()를 직접 쓰면 복잡도가 줄어들고 코드가 오히려 명확해집니다 — 전형적인 pass-through 징후.

추가 마찰: nutrition.policy 패키지가 diet.recommendation.candidate.DietRecommendationCandidate를 import합니다. 상위(nutrition) → 하위(diet candidate) 역방향 의존성입니다.

⛔ Before

// nutrition/policy/
class NutrientCompletenessPolicy {
  boolean isComplete(
    Goal.GoalType goalType,   // 사용 안 됨
    DietRecommendationCandidate candidate
  ) {
    return candidate.macroDataComplete(); // 그게 전부
  }
}

// 호출부
if (policy.isComplete(goal.getGoalType(), candidate)) {
  ...
}

✅ After (Option A — 인라인)

// NutrientCompletenessPolicy 삭제

// 호출부에서 직접 표현
if (candidate.macroDataComplete()) {
  ...
}

// 또는 GoalType 분기가 실제로 생길 때
// 다시 추출 (YAGNI 원칙)

✅ After (Option B — 타입 경량화)

// GoalType별 차이가 정말 필요하다면:
sealed interface MacroRequirement {
  boolean isSatisfiedBy(boolean macroComplete,
                         double proteinRatio);
  record Standard() implements MacroRequirement { ... }
  record HighProtein() implements MacroRequirement { ... }
}
// GoalType → MacroRequirement 팩토리만 필요

  • 지역성(Locality): 매크로 완전성 판단이 DietRecommendationCandidate에 집중됩니다
  • 역방향 의존성 제거: nutrition 패키지가 diet candidate 세부를 알 필요 없음

② VerificationPriorityService

인라인 우선순위 공식 + 매크로 완전성 검사 이중 정의

로직 집중도

관련 파일

domain/diet/admin/VerificationPriorityService.java domain/diet/entity/FoodCatalog.java (4-null check)

⚠ 문제 1 — isMacroComplete() 이중 정의

VerificationPriorityService.isMacroComplete(FoodCatalog food)는 calories · protein · carbs · fat 모두 null 아닌지 직접 검사합니다. 같은 판단이 DietRecommendationCandidate.from() 내 macroDataComplete() 필드 계산에서도 이미 수행됩니다. 두 곳이 독립적으로 변경될 경우 불일치가 발생합니다.

⚠ 문제 2 — 이름 없는 우선순위 공식

score = usageCount × macroWeight × allergenWeight는 서비스 메서드 내에 하드코딩되어 있습니다. "우선순위"라는 도메인 개념이 없어 가중치를 조정하려면 서비스를 직접 편집해야 하고, 점수 계산 로직을 단독으로 테스트할 방법이 없습니다.

⛔ Before 코드

// VerificationPriorityService
private boolean isMacroComplete(FoodCatalog food) {
  return food.getCaloriesPer100g() != null  // ← 중복
      && food.getProteinPer100g() != null
      && food.getCarbsPer100g() != null
      && food.getFatPer100g() != null;
}

double score = food.getUsageCount()
    * (isMacroComplete(food) ? 1.0 : 2.0)  // 이름 없음
    * (tagged ? 1.0 : 2.0);

✅ After 코드

// FoodCatalog에 단일 정의
public boolean isMacroComplete() {
  return caloriesPer100g != null
      && proteinPer100g != null
      && carbsPer100g != null
      && fatPer100g != null;
}

// VerificationPriorityScore (새 record)
record VerificationPriorityScore(
  long usageCount, boolean macroComplete, boolean tagged
) {
  double value() {
    return usageCount
        * (macroComplete ? 1.0 : 2.0)
        * (tagged ? 1.0 : 2.0);
  }
}
// 서비스는 record 생성 + value() 호출만

📈 기대 효과

  • 지역성: 매크로 완전성 판단이 FoodCatalog 한 곳으로 집중
  • 테스트 표면: VerificationPriorityScore를 독립적으로 단위테스트 가능
  • 가중치 튜닝: 서비스를 편집하지 않고 record 생성자 또는 설정으로 조정 가능

③ DietRecommendationCandidatePool

숨겨진 CandidateRestrictions 솔기(Seam)

관련 파일

recommendation/candidate/DietRecommendationCandidatePool.java

⚠ 문제

CandidateRestrictions는 DietRecommendationCandidatePool의 private inner record입니다. 이 레코드는 List<DietRestriction>을 4가지 TargetType으로 파싱·정규화하는 의미 있는 책임을 집니다. 하지만 DietRecommendationCandidatePool 테스트 없이는 이 파싱 로직을 직접 테스트할 방법이 없습니다.

단, 현재는 가설적 솔기(1개 어댑터)입니다. 다른 서비스가 같은 파싱을 필요로 할 때 실제 솔기가 됩니다(2개 어댑터 기준). 지금 당장의 추출은 과도한 추상화일 수 있습니다.

📈 기대 효과

  • 테스트 표면: 파싱 로직을 DietRecommendationCandidatePool 없이 단위테스트 가능
  • 지역성: DietRestriction → 4가지 집합으로의 변환 로직이 명시적인 타입을 가짐
  • 재사용: 두 번째 호출자 등장 시 즉시 공유 가능

④ DataFreshnessPolicy

소스별 만료 창의 외부 확장 준비도

관련 파일

domain/diet/policy/DataFreshnessPolicy.java

💡 관찰

DataFreshnessPolicy는 현재 잘 설계된 깊은 모듈입니다 — Clock 주입 가능, 소스별 명시적 만료 규칙, NEVER_EXPIRES 분기 명확. 테스트도 DataFreshnessPolicyTest에서 경계값을 커버합니다.

투기적 마찰점: 만료 창(730일, 365일)이 하드코딩되어 있습니다. 새 소스가 추가될 때마다 switch 분기를 편집해야 합니다. 이것은 현재는 감수할 만하지만, 소스 종류가 늘어나면 enum → 설정 맵 또는 policy record 패턴이 유용해질 수 있습니다.

현재 권장사항: 변경하지 마세요. 마찰이 실제로 느껴질 때 다시 검토하세요.

현재 (지금은 괜찮음)

switch (food.getSource()) {
  case SEED, USER_CUSTOM ->
    { return true; }           // ∞
  case MFDS_STANDARD_PROCESSED,
       MFDS_STANDARD_DISH,
       MFDS_FOOD_NUTRIENT_DB  ->
    maxAge = Duration.ofDays(730); // 하드코딩
  case BRAND_OFFICIAL         ->
    maxAge = Duration.ofDays(365);
  ...
}

소스 증가 시 고려 (미래)

🏆 최우선 추천

① NutrientCompletenessPolicy 제거

가장 명확한 ROI입니다. 이 클래스는 지금 당장 제거해도 동작이 전혀 바뀌지 않습니다. GoalType 파라미터는 이미 거짓 약속이고, 역방향 패키지 의존성(nutrition → diet.candidate)까지 있습니다. 제거하면 호출부가 더 명확해지고 의존성 방향이 정상화됩니다.

② VerificationPriorityService는 두 번째로 처리하세요. FoodCatalog.isMacroComplete() 단일 정의로 수렴하면 불일치 가능성이 없어지고 서비스 로직이 훨씬 읽기 쉬워집니다.
