Architecture Review

Gainsy diet 도메인 전체 아키텍처 검토

기준 문서인 CONTEXT.md, 식단 추천 관련 ADR, 실행 계획, 그리고 backend/src/main/java/com/healthcare/domain/diet 코드를 함께 읽고 정리한 개선 후보입니다. 관점은 “Module이 충분히 Deep한가”, “Interface가 호출자에게 구현 세부를 얼마나 요구하는가”, “Locality와 Leverage를 높일 수 있는가”입니다.

검토 기준

Deep Module / Shallow Module

삭제 사고 실험, ADR 적합성, 테스트 우회 여부를 함께 보았습니다.

가장 강한 신호

추천 후보 자격 + Allergen Evidence

ADR-0005와 현재 구현 사이의 차이가 가장 큰 축입니다.

리포트 결과

Strong 4개, Worth exploring 2개

첫 탐색은 후보 1번을 추천합니다.

요약 판단

diet 도메인은 문서와 ADR이 이미 좋은 편입니다. 그래서 새 Module을 많이 늘리는 것보다, 이미 존재하는 추천 후보 풀, AllergenSafetyGate, Recommendation Snapshot and Event, Food Catalog Ingest Run의 Depth를 키워 호출자가 구현 세부를 덜 알게 만드는 쪽이 더 높은 Leverage를 가집니다.

Problem

`DietRecommendationCandidatePool`의 Interface가 “검증된 추천 후보”를 보장하지 못해 `DailyDietRecommendationUseCases`가 `macroDataComplete`, `hasVerifiedServingOptions`를 다시 알아야 합니다. 후보 자격 Implementation 일부가 호출자로 새고 있어 후보 풀 Module의 Depth가 부족합니다.

Before

  U["DailyDietRecommendationUseCases"] --> P["DietRecommendationCandidatePool"]
  P --> A["AllergenSafetyGate"]
  P --> C["Catalog / Serving Option 조회"]
  U --> F["macro / serving 재필터"]
  F --> E["ConstraintRecommendationEngine"]

After

flowchart LR
  U["DailyDietRecommendationUseCases"] --> Q["Verified Recommendation Candidate Qualification Module"]
  Q --> P["DietRecommendationCandidatePool"]
  Q --> A["Allergen Evidence / Profile 판단"]
  Q --> V["검증된 추천 후보 값"]

Solution

후보 자격 판정을 후보 풀 근처의 Deep Module로 모으고, UseCase는 추천 orchestration만 알게 합니다.

Locality / Leverage

자격 조건 변경이 한 Module에 모이고, 엔진·관리자 리포트·벤치마크가 같은 판단을 재사용할 수 있습니다.

Tests

UseCase 재필터 제거 회귀, 후보 풀 자격 결과, 엔진 테스트 fixture의 우회 생성 방지를 확인합니다.
