이점

  • • 인터페이스 파일 2개 삭제
  • • leverage: BatchRunner가 진짜 배치 로직을 가짐
  • • 테스트에서 람다로 즉시 주입 가능
  • • 새 소스 추가 시 별도 클래스 불필요

문제

FoodEntrySource는 검색·AI 추정·커스텀 등록을 하나의 ObservableObject에서 처리한다. 인터페이스(퍼블리시드 변수 7개 + 메서드 6개)가 구현만큼 넓다 — 얕다. Task 취소 로직이 분산되어 인터리브 버그가 숨기 쉽다.

해결

sealed FoodEntryState enum과 FoodEntryAction을 도입. FoodEntrySource가 @Published var state 하나만 노출하고, 전이는 send(_ action:)으로 직렬화.

이점

  • • interface 면적: 변수 7개+메서드 6개 → state 1개+send 1개
  • • locality: Task 취소·인터리브 버그가 send() 한 곳에 집중
  • • 테스트: state 전이를 단언 가능
  • • 불가능한 상태 컴파일 타임에 차단

  • • 테스트에서 네트워크 없이 식품 검색 검증 가능
  • • locality: 커스텀 식품 필드 변경이 Request struct 한 곳에 집중
  • • 런타임 직렬화 오류 제거

Top Recommendation

Candidate 4 — iOS FoodEntrySource sealed 상태 기계

FoodEntrySource는 현재 Phase 5에서 가장 넓은 인터페이스를 가진 얕은 모듈이다. 퍼블리시드 변수 7개와 메서드 6개로 이뤄진 인터페이스는 구현과 거의 같은 크기라서 leverage가 없다. 검색·AI 추정·커스텀 등록이 경쟁하는 Task 취소 버그는 재현이 어렵고, 이 구조에서는 테스트로 잡기도 어렵다. sealed FoodEntryState로 인터페이스를 @Published var state 하나로 줄이면, 상태 전이가 locality를 얻고 뷰 코드가 단일 관찰점을 갖는다. Candidate 1(FoodCatalogPublicDataImportService 제거)은 더 단순하지만, Phase 5 이후 실제 마찰이 더 크게 남아있는 곳은 iOS다.
